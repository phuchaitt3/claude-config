# Working rules (all projects)

Loaded in every session through `~/.claude/CLAUDE.md`. This file holds only what applies to every task; procedures for specific situations live in the `workflow` plugin's skills and load when needed (standard: keep always-loaded instructions short and move task-specific detail to on-demand skills, since compliance falls as the instruction count rises, IFScale arXiv 2507.11538; checked 2026-10-30). A project's `CLAUDE.md` adds to these and may make them stricter; nothing here relaxes a limit a project sets, except the self-drive free-quota exception in the third Hard limit and the self-drive deploy and new-repository exceptions in the first (a project's own ask-before-deploy rule still wins until its PR changes it).

## Hard limits (a project may tighten, never loosen, except through the exceptions named here)

- Ask before anything destructive (deleting or overwriting data you did not create, rewriting git history, force-pushing) and anything outward-facing (merging a PR, pushing to `main` or to a public repository, publishing, uploading to any external service, spending money). Exceptions: pushing your own feature branch and opening its PR ("Git"); merges in a confirmed solo-fast project (`workflow:pr-review`); the config repo ("Git"); commits and pushes to `main` in a confirmed direct-tier project (`workflow:new-project`; user's decision, 2026-11-05); pushes to `main` in a repository the user opted in with the local git setting `git config claude.pushDefault allow`, for private notes repositories such as a handoff folder (user's decision, 2026-11-09); during a self-drive run, at any hour (`workflow:self-drive`, "Overnight mode"), deploying to a free-tier stack with tools already signed in (never reading credential files, never spending money) and creating a new GitHub repository under the user's account (user's decision, 2026-11-14; any self-drive run, 2026-11-27; a project's `CLAUDE.md` that says to ask before deploying still applies until its own PR changes it).
- Never read, write or delete credential files (`~/.kaggle`, `.env` files holding secrets, tokens, `~/.claude/.credentials.json`). Read and update `.env.example` instead.
- Ask before a long paid or cloud job. The default threshold is 30 minutes; a project may set another. Exception: during a self-drive run, at any hour (`workflow:self-drive`, "Overnight mode"), a job on a free cloud quota (Kaggle, Colab free tier) needs no ask, whatever its length and whatever threshold a project's `CLAUDE.md` sets; the worst case is the quota running out. Outside a self-drive run, and for any job that spends money, ask as before (user's decision, 2026-11-14; extended to override project thresholds, 2026-11-14; any self-drive run, 2026-11-27).
- **Kaggle first** (user's decision, 2026-11-16: overnight; widened the same day to every heavy job, day and night, keeping the daytime ask): a GPU job, or a CPU job expected to take over 30 minutes, runs on the free Kaggle quota when it can, to keep heat and risk off the local machines (standard: findings/laptop-overnight-heavy-jobs, checked 2026-11-16). It runs locally only when: it measures the laptop itself (a timing or memory benchmark of this machine, or the weekly cooling reference in `scripts/laptop_health.py`); it needs a local service (Docker stack, Ollama, a database) or data the project has not already put on Kaggle; it exceeds Kaggle's limits (session length, GPU memory, weekly quota left); the project has no Kaggle runner yet; or the project's `CLAUDE.md` says local. The ask rules above are unchanged: outside a self-drive run a Kaggle run expected to take over 30 minutes still asks first, which also guards the weekly GPU quota; a self-drive run needs no ask. The run summary (self-drive) or the reply (otherwise) names each local heavy job and which reason applied. A project without a runner whose heavy jobs repeat gets an issue to add one.
- Background commands keep the machine awake automatically: the `keep_awake` hook holds off idle sleep until each one exits and the turn that reads its result ends, skips recognised long-lived servers (`# keepawake: on|off` overrides), and lists active holds in the prompt status line. A long job started any other way (foreground, Task Scheduler, a separate terminal) goes through the keep-awake wrapper (`keepawake.ps1` in `workflow:scaling-test`). Never change the user's power plan (user's decision, 2026-11-09, after a laptop sleep spoiled a benchmark repeat; hook replaces the 10-minute threshold, 2026-11-11; hold through the next turn, 2026-11-11, after the laptop slept one second after a run and the next step waited 5.5 hours; standard: findings/keep-awake-long-jobs, checked 2026-11-11).
- **Run-time estimates** (user's decision, 2026-11-11): a command expected to take over 10 minutes carries `# estimate: <N>m` (also `s`, `h`). The `run_estimate` hook logs estimate and actual time to `~/.claude/run-estimates.jsonl` (local, never committed) and, once three tagged runs exist, shows the past actual/estimate ratio; apply any approval threshold to the estimate scaled by that ratio.
- **Smoke test first** (user's decision, 2026-11-18, after a 10-minute heat run failed on a wrong task name): a command estimated over 5 minutes is first run in a short form that exercises every step end to end (a `--smoke` flag, seconds, nothing logged as a result), then started as the real run tagged `# smoke: <what ran>`, or `# smoke: none (<reason>)` when the job has no short form; unit tests of the parts do not count. The `smoke_test_check` hook reminds a chat when a command tagged `# estimate:` over 5 minutes has no `# smoke:` tag; it never blocks.
- **GPU lock** (user's decision, 2026-11-12; services added 2026-11-13): a GPU job on this machine runs under the machine-wide lock: through `python ~/claude-config/scripts/gpu_run.py run --wait -- <command>`, or through the project's own guard when it has one (it shares the same lock). A GPU container or model server that keeps running after its start command returns (`docker run -d --gpus`, `docker compose up -d` with a GPU service) starts through `gpu_run.py hold --wait --purpose <task> -- <command>`, which holds the lock until those containers stop; a `docker run` GPU container gets a `--name` or `--label` naming the task, and is stopped when the task no longer needs it. The `gpu_guard` hook refuses an unguarded GPU container start, and `timeout` around any foreground `docker run` or `compose run`/`up`, GPU or not: killing the client leaves the container running; use `hold --max-minutes N` or stop the named container yourself (user's decision, 2026-11-13; standard: findings/docker-run-timeout-cleanup, checked 2026-11-13). Ollama loads models onto the GPU outside the lock: `run` and `hold` unload what it has loaded when they take the lock (`--keep-ollama` opts out). Never bypass the lock. To see how the GPU was shared, run `gpu_run.py report` (jobs, refusals, waits, unguarded use); `gpu_run.py check` flags the GPU busy with no lock held (standard: findings/shared-gpu-one-machine, checked 2026-11-13).
- **Docker cleanup** (user's decision, 2026-11-14, after eight stopped containers from finished tasks were found): a chat that starts a container or compose project for a task removes it when the task ends: `docker compose -p <project> down --rmi local`, which also removes the images it built (never `-v`; volumes stay until the user says; `--rmi local` added 2026-11-26, user's decision) or `docker rm -f <name>`. The `docker_cleanup` hook records what this chat started and, at the end of a turn, blocks once while any of it still exists; a container kept on purpose (a held GPU service) is named with its reason in the final message. Never delete volumes without the user's yes (`workflow:docker`).
- **Own processes** (user's decision, 2026-11-28, after an Ollama app that a chat's own `ollama list` had started held a benchmark waiting for memory): a chat may stop a process or app that it started itself and no longer needs, without asking. It names it by process ID, after checking the start time against its own command, and says so in the reply. Anything it did not start, or cannot prove it started, or that another job is using, still needs the user's yes.
- **Tools come from images or package managers** (user's decision, 2026-11-17, after a downloaded llama.cpp server blocked an overnight run for two days): an agent installs a tool or model server from an official or digest-pinned Docker image or a package manager (pip, uv, npm, winget), never by downloading and running a loose binary or archive; a tool with no such route becomes a `needs-you` item naming the exact download and checksum. An agent never edits `settings.json` permissions itself. Detail and the llama.cpp example: `workflow:docker`.
- **Heavy RAM/CPU jobs** (user's decision, 2026-11-14; GPU jobs, memory check and Compose stacks added 2026-11-17): a full test suite, a build, or a load of a large model or dataset into system RAM, however short, goes through `python ~/claude-config/scripts/gpu_run.py run --resource ram --wait -- <command>`, so two chats never run one at once on one 16 GB machine. A GPU `run` or `hold` takes the RAM lock itself, first, so a GPU job needs no outer wrapper. Whoever takes the RAM lock waits while free memory (commit headroom) is under 4 GB, because chats, editors and Docker use memory no lock counts (standard: findings/memory-admission-one-machine, checked 2026-11-17). A Docker Compose stack starts through `gpu_run.py hold --resource ram --wait --purpose <task> -- docker compose up -d` (a stack with a GPU service: plain `hold`), which holds the lock until the stack stops. Ordinary commands (git, linters, a single test file) need no lock (standard: findings/agent-process-and-resource-control, checked 2026-11-12). The `ram_guard` hook refuses a full test run, a build or a `docker compose up` started outside the lock; a model or dataset load inside a script is not visible to it and stays the agent's judgement (user's decision, 2026-11-15).
- **Which machine** (user's decision, 2026-11-23; benchmark: findings/laptop-vs-pc-benchmark; PC first, Kaggle first kept): the lock, memory and Kaggle-first rules apply on each machine separately and in the same order. Kaggle-first decides first: a job it sends to Kaggle runs there, from whichever machine. Only a job that runs locally gets a machine: the PC when its session is listed in `ListAgents` and idle (PC time against the laptop's: tests 0.66, memory load 1.10, GPU 1.36 to 1.47), otherwise the laptop. A job that measures the laptop itself, needs a laptop-only service or file, or runs while the PC is off runs on the laptop. A PC job needs the same locks (`gpu_run.py` on the PC) and a smoke test first, and the reply names the machine used. Before reading or acting on machine state, take the machine from the `machine_check` hook line, never from the user's wording or a rule's. If the request names the other machine, say so first and ask which is meant (user's decision, 2026-11-28).

## Decision rights

The test is reversibility: if a choice can be undone with a revert, a rerun or a file edit, make it. Asking stops the flow, so ask only when a wrong guess is expensive or only the user knows the answer.

- **Decide and proceed:** implementation choices, task order, which chat or subagent does a task, commits on your feature branch, defaults for open questions, doc fixes, stale facts, tests, lint and format, coordination files.
- **Decide, then tell** (one line in the reply or the project's DONE.md, with the reason and the undo): a default on an open design question; a changed pinned version, preset or tolerance, with the run that justifies it; reordered or added milestones.
- **Ask first:** everything under Hard limits; choices only the user can judge (thesis or paper claims, licensing, public content, a budget); relaxing a project's limit; **adding or changing any rule** (user's decision, 2026-10-29): load `workflow:rule-change` before proposing one.

**Review mode** (user's decision, 2026-11-01): one global setting, `settings/review.json`, says how a PR is checked before an agent merges it (`peer`, `self-review`, `self-diff`, `ci-only`; `workflow:pr-review`, "Review modes"). The `review_mode` hook announces it. The user changes it; a chat edits it only when the user asks.

When unsure, take the lower-asking tier if the action is reversible. Do not ask for confirmation of something already requested, or which of two reversible options to take.

**How to ask:** a choice among 2–4 options goes through `AskUserQuestion`, recommended option first and marked "(Recommended)", one self-contained question per decision. Plain text only for open questions or when the tool is unavailable. Decisions that can wait become `needs-you` issues ("Replies").

**Unclear requests** (user's decision, 2026-10-30): ask one clarifying question first only when the request has two plausible readings, they lead to substantially different work, and the conversation, code and project files do not settle it; a term that fits two things in context (two hooks, two PRs) counts. Otherwise state "Reading X as Y" in one line and proceed.

## Replies and items for the user

- **Push only what blocks the task in hand.** End a turn with at most 3 lines: the step that blocks the current task (plain words, a link, the time it takes); "N new in [INBOX.md](…)" only if the inbox gained an item this turn; a `/clear` or `/compact` suggestion only when "Context" says so. Say nothing when nothing blocks. Never end with a bare list of IDs.
- **Items for the user live on GitHub** (user's decision, 2026-10-30): a PR or issue labelled `needs-you`, with the user as reviewer or assignee. The body says what it is, why it needs the user, the exact action, the time it takes, and what happens if nothing is done. In a public repo, private content stays in a local ticket and the issue says only "private item; ask in chat". Handoff files are the agents' notes; never ask the user to read them.
- **Status comes from `gh` in the same turn**, never from memory or a handoff file (user's decision, 2026-10-30). The same holds for any live state (running chats and sessions, processes, background jobs, locks): read it from its source in the turn you state it, never from an earlier reading; the `session_state` hook adds a fresh line of running Claude sessions to each message when it changes (user's decision, 2026-11-15, after a stale listing undercounted overnight runs). The `stale_claim` hook backs this for one case: a final reply that asks the user to act on a PR or issue already merged or closed (2026-11-11; standard: findings/agent-state-freshness, checked 2026-11-11).
- **Facts have one source** (user's decision, 2026-11-09): a file that restates a fact kept elsewhere (a doc, a run, an issue) names that source by path and section. Before relying on a restated fact, read its source. When you change a fact at its source, search the repositories that cite it for that path and section, and update or remove the copies in the same turn. This widens "Status comes from gh" to any fact (standard: findings/policy-single-source, checked 2026-11-01).
- **Markdown** (user's decision, 2026-11-05, replacing the `==Heading==` form of 2026-10-30): in chat replies, no `#` or `##` headings; when a reply needs sections, use a bold label on its own line (`**Label**`); short answers are plain paragraphs with no headings. Files keep normal `#` headings.

## Git

- **Always:** one GitHub issue per task, its PR says `Closes #n`; commit on a feature branch, never on `main` (except the config repo and a confirmed direct-tier project); never `--force`; agents write to GitHub as `phuchai-bot` (check `gh auth status`, never `gh auth switch`). Load `workflow:git` before committing, pushing, opening a PR or issue, switching machines, or changing the config repo (commit rules, push conditions, wip commits, config-repo procedure).

## Model and effort

The user picks the model and effort. At the start of each task, say in one line which it needs, tagged `[Sonnet, medium, no plan mode: reason]`, and say so if the current model is a poor fit; the same tag goes on every proposed next step and decision item. Sonnet is the default for routine work; Opus is fine for a truly complex or important task, chosen up front when Sonnet would likely need more than one try (user's decision, 2026-11-15; standard: findings/agent-model-effort-selection, checked 2026-11-15). An Opus tag names the difficulty (for example "unfamiliar domain", "bug across several components"); "new feature" alone is not a reason. `max` effort only when the user asks. Plan mode only when the design is still open.

Table of model and effort by task type: `workflow:model-effort`.

## Context

**Task boundary** (every chat, self-drive included; user's decision, 2026-11-28, after a handover left a run's issue half done). The current task is done (its PR merged, or waiting only on someone else), parked, or waiting only on a run that a new chat can collect from written notes. A PR for one step of a bigger task is not a boundary, and the middle of a debugging thread never is. Over the limit in `settings/context.json`: start no new task, finish the current one, then switch (an interactive chat suggests `/clear` or `/compact`; a self-drive chat hands over). A chat that hands itself over does so anyway at `ceiling_tokens`, or `ceiling_minutes` after the first reading over the limit, and names what is unfinished.

The user sees the context meter in the status line; you do not. Suggest once per task boundary, in one line at the end of the message, never in the middle of a debugging thread:

- `/clear` with a resume prompt (chat name, folder, branch, next task with its tag) when the next task is unrelated (standard: findings/claude-code-clear-vs-compact, checked 2026-11-13) or when quality is slipping (the same correction twice; standard: findings/claude-code-clear-vs-compact, checked 2026-11-13). Do not start the next task in that turn.
- `/compact <what to keep>` only when the task continues (standard: findings/claude-code-clear-vs-compact, checked 2026-11-13) and its state cannot be written to files yet; write ruled-out causes to a file first, because a summary can distort them (the last two clauses are the user's own; no source found).
- When the `context_nudge_check` reminder arrives with a message that starts an unrelated task, ask before starting it: `/clear` and resend, or "go" to do it here (user's decision, 2026-11-27; standard: findings/claude-code-clear-vs-compact, checked 2026-11-13; the limit is `limit_tokens` in `settings/context.json`, the user's choice with no source).

## Industry practice (user's decision, 2026-11-01)

Before proposing or adding a check that can block work (a CI check, a merge gate, a refusing hook), check the practice for it: answer from a current findings entry, otherwise search and write the entry in the same turn, and give the recommendation with its tag (user's decision, 2026-11-28).

Before searching the web for an established practice (software, research methods, hiring or any other field), read `~/claude-config/findings/README.md`. If a current entry covers the question and today is before its Review by date in the index (`checked` plus `review_months`, 12 unless set; user's decision, 2026-11-15), answer from it and cite it; do not search. A page the fetch tool refuses (Reddit, forums such as Voz) is read with the user's own `webx` tool (`D:\1.git_projs\webx\main`): read the section "Reddit and other sources the agent cannot read" in the same README first, then follow it; never get round a 403 by other means such as web archives (user's decision, 2026-11-24, after a chat did not know the tool and tried an archive copy, which the permission classifier refused). After a search that checks a practice, add or update the entry in the same turn (front matter, finding in a few lines, source links, date, limits of the sources; then run `scripts/build_findings_index.py`, which rebuilds the index) and tag the point where it is written: `(standard: findings/<topic>, checked YYYY-MM-DD)`. The register names no project and holds no private detail: the repository is public.

## Skills to load (the `workflow` plugin)

- `workflow:git`: before committing, pushing, opening a PR or issue, switching machines, or changing the config repo.
- `workflow:dvc`: before running or changing DVC-tracked data, before removing a worktree that may hold run outputs, or when setting up data versioning.
- `workflow:pr-review`: before opening, reviewing or merging a pull request, or deferring work out of one.
- `workflow:new-project`: at the start of a project (tier, mode, one-time GitHub setup, the bot's push config), or when adding environment settings or a `.env`.
- `workflow:multi-chat`: when a SessionStart notice says other chats are running (any repository): the short core. `workflow:multi-chat-repo`: when several chats share a repository, or the project's `CLAUDE.md` names an inbox or handoff folder.
- `workflow:rule-change`: before proposing or editing any rule, here or in a project, and for any proposal with more than about five items.
- `workflow:subagents`: before dispatching a subagent (only when the user asks or a project rule allows).
- `workflow:adr`: before writing, rewriting or editing an ADR, or answering a review question on one.
- `workflow:experiment`: before trying a new implementation that might replace a working, accepted one, or adding a feature flag or experimental mode.
- `workflow:self-drive`: when the user asks a chat to pick tasks and loop without prompts (per chat, user-started only).
- `workflow:focus`: when the user says "focus mode" or "talk mode", or types /focus or /talk (a chat peers leave alone: it does normal work but never reviews, and answers peers only about its own claims and PRs).
- A project whose recorded mode is not **build**: read `~/claude-config/modes/<mode>.md` before starting work.
