# Running several coding agents overnight to get more work done

- **Question:** Does letting several Claude Code agents run overnight, unattended, get more work out of a subscription, and what do practitioners set up so the result is usable in the morning?

- **Finding:**
  - **Overnight runs use time, not extra quota.** Pro and Max have a five-hour session limit and a weekly limit, shared across Claude chat, Claude Code and the IDE (official help page). Scheduled cloud tasks "draw down subscription usage the same way interactive sessions do" (official docs). So overnight work adds output only when five-hour windows would otherwise go unused while the weekly limit still has room; once the weekly limit binds, overnight work is taken from daytime work. Parallel agents drain the windows faster rather than adding to them (one guide: "watch your quota, since parallel agents consume it quickly"). Past the limit, runs stop unless usage credits or API credits are turned on, which costs money (official). Secondary sources disagree on exactly when the weekly limit resets, so check `/status` or the usage page rather than a blog.
  - **Ways to run with nobody there.** (1) Cloud scheduled tasks (formerly routines; research preview): a saved prompt plus repositories that runs hourly, nightly or once, on Anthropic's machines, so the laptop can be off. Runs start in auto mode; changes go to `claude/`-prefixed branches; at most one run per hour per schedule (cron faster than hourly is rejected); account caps are 100 scheduled runs per hour. Earlier secondary sources quote daily caps of 5/15/25 runs; the current docs give hourly caps instead (official docs, checked 2026-11-13). (2) Local headless runs (`claude -p`) in a shell loop, the "Ralph" pattern, which needs the machine awake (see `findings/keep-awake-long-jobs`) and permission rules set in advance, because a permission prompt stalls the loop until morning. `/loop` is session-scoped: it needs the machine on and the session open, a self-paced loop is stopped with Esc while it waits, recurring tasks expire after 7 days, and an iteration that neither reschedules nor stops ends the loop after one fallback wakeup about 20 minutes later (official docs). The docs say nothing on what a wakeup does at a usage limit; issue reports say a wakeup can fire into a live limit, that a loop cannot be stopped while the limit blocks inference, and (June 2026) that a pending wakeup survived Ctrl+C. Treat resume after a limit as unverified.
  - **Task choice decides whether it pays.** Guides agree: pick work with a machine-checkable finish line that splits into small pieces (test migrations, coverage pushes, a well-specified backlog); keep out judgment calls, unclear success criteria, production debugging, and anything irreversible (deploys, data, infrastructure). Auth, payments, data models and public APIs wait for daylight. Reports of large overnight output (a hackathon team's "1,000+ commits") are greenfield work with clear specs and are anecdotal.
  - **Limits the agent cannot change.** Bound every run by iteration count, spend, wall-clock time and stall detection (no progress on the failing tests), and make the loop record which limit fired. An iteration count does not bound cost, because iterations and subagents vary; `--max-budget-usd` caps one print-mode run. Don't raise a limit by reflex.
  - **Isolation for several agents.** One worktree and branch per agent, file ownership split before the start, branches integrated one at a time with full checks after each. Worktrees do not isolate databases, ports, caches or the GPU (see `findings/agent-process-and-resource-control`, `findings/shared-gpu-one-machine`). Two agents taking the same task is a reported common failure, so claims must be settled before the night starts.
  - **Review is the bottleneck the next morning.** Several sources say agents move the constraint from writing to reviewing: "overnight dispatch is budgeted by tomorrow's review capacity". Recommended per-run output: a short receipt (how the agent read the task, key decisions, real test and lint output, what it skipped, anomalies) and a deferred-questions file instead of guessing or halting; triage in two passes (merge, fix or kill, then full review by risk), with killing a wrong branch treated as normal. An MSR '26 study of 33,707 agent-authored PRs found about 28% merge almost at once, and that large, unplanned, multi-component changes predict review effort and abandonment; a stated plan predicts less abandonment.
  - **Checker's inference:** on a small plan whose weekly limit already binds, overnight agents mostly shift work in time; the gain comes from (a) unused five-hour windows overnight, (b) work that needs wall-clock time rather than tokens (long tests, benchmarks, builds), and (c) arriving in the morning with a review queue sized to what can be read. More agents than the morning can review is negative value.

- **Evidence strength:** official standard for limits and scheduled-task behaviour (Anthropic docs); common practice for task choice, limits and worktrees (several independent guides agree); anecdotal for output and cost figures; one peer-reviewed study for PR review effort.
