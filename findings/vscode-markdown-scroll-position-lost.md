# VS Code: Markdown file jumps to the top after switching files

- **Question:** Opening another file and returning to a `.md` file puts the view at a fixed wrong place (the top, or one heading) instead of where it was. Is there a fix, and which settings apply? Separate from the other VS Code entries because those cover the terminal, not the editor.
- **Short answer (tested on one machine, VS Code 1.148.0, 2026-11-25):** the plain text view of a `.md` file jumps because the custom-editor preview of that file was scrolled earlier; VS Code keeps that line in memory and returns the text view to it. Fix: close that preview tab, run `Developer: Restart Extension Host` (Ctrl+Shift+P). The earlier advice to use `Markdown: Open Preview` instead is **withdrawn** (2026-11-25, same day): that preview is one shared view that follows the active text file. **To read several rendered files and keep each place**, open each `.md` as its own rendered tab and turn off preview tabs, in the repository's `.vscode/settings.json` (the opened folder must be the one holding it): `"workbench.editorAssociations": {"*.md": "vscode.markdown.preview.editor", "**/{draft,read}.md": "default"}` (the second pattern names files to edit as text) and `"workbench.editor.enablePreview": false`. Close the tabs that are already open and open the files again. Tested in a throwaway profile, see "Per-file rendered tabs".
- **If it comes back, in this order:**
  1. Ask which view jumps (text or preview) and how the file was left and re-entered (tab click or file list).
  2. Check that the file did not change on disk (`stat`, `git log -- <file>`).
  3. Read a **copy** of `%APPDATA%/Code/User/workspaceStorage/<hash>/state.vscdb` (SQLite, table `ItemTable`; the hash is the folder whose `workspace.json` names the workspace). Key `memento/workbench.parts.editor` lists the open tabs: a `webviewEditor` with `viewType` `vscode.markdown.preview.editor` is the preview that causes this, and its `state` holds `line`. Key `memento/workbench.editors.files.textFileEditor` holds the text view's saved `firstPosition` per group. If the landing line equals the preview's `line`, it is this cause. The file is written with a delay, so note its modified time.
  4. Test: scroll the preview to a heading in the **middle**, scroll the text view to the end, click another file's tab and come back. Landing on that heading confirms it. Do not use the top: a freshly opened file also starts there.
  5. Apply the fix above. If it still jumps, the cause is different, or a VS Code update changed the code: search the bundled `dist/extension.js` for `getPreviousStaticEditorLineByUri`.
- **What did not help or cost too much:** a new editor group (the line is stored per file, not per group); resetting the workspace state folder (worked once, came back the same day, loses the window's open files, terminals and sign-in).
- **Finding:**
  - The text editor remembers scroll position and cursor by default: `workbench.editor.restoreViewState` is `true`. The state is stored per editor group and discarded when the group closes. `workbench.editor.sharedViewState` (default `false`) reuses the most recent state across groups when a group has none. (standard: findings/vscode-markdown-scroll-position-lost, checked 2026-11-25; source: VS Code source, `workbench.contribution.ts`.)
  - `workbench.editor.enablePreview` (default `true`) replaces an italic-titled preview tab with the next file opened. The setting text says only that the contents are replaced. Whether a replaced tab still gets its scroll back depends on the view-state setting above; the sources do not say. (inference: findings/vscode-markdown-scroll-position-lost)
  - The Markdown preview (the rendered view) is a separate case. VS Code issue 63690 ("markdown files preview does not save scroll position", 2018) was closed as fixed in 2021 by a maintainer. A commenter on the same day said the release-notes preview still lost its position, and the issue gives no later confirmation either way. The preview-as-custom-editor work (issues 84520 and 138040) says scroll position is synced between preview and editor only when both are not visible at once.
  - A VS Code fork's forum (Cursor) reports the same symptom for Markdown files in 2026 and says a fix covered one tab, not switching between files. That is a fork, not VS Code.
  - **Cause found in the installed code (1.148.0, bundled `markdown-language-features/dist/extension.js`, read 2026-11-25):** the custom-editor preview (`vscode.markdown.preview.editor`, what `Markdown: Reopen as Preview` opens) stores its scroll line per file in memory (`setPreviousStaticEditorLine`) each time it scrolls. A handler on `onDidChangeActiveTextEditor` then scrolls the plain text editor to that line each time the file becomes the active editor. The entry is only ever set, never cleared, in the class that holds it, and neither `markdown.preview.scrollEditorWithPreview` nor `scrollPreviewWithEditor` is checked on that path. So a file once scrolled in that preview always returns to the preview's last line in the text editor. Observed once: the text editor landed on line 69 while the preview tab's stored line was 69.51, in a fresh editor group too. Confirmed by a test predicted in advance (one machine, 2026-11-25): preview scrolled to a chosen mid-file heading, text editor scrolled to the end, another file opened and left; the text editor landed on that heading. A first version of the test used the top of the file and proved nothing, because a freshly opened file also starts there. The extension is built in, so `--disable-extensions` does not remove it.
  - The other preview (`markdown.showPreview`, "Markdown: Open Preview", view type `markdown.preview`) does not write that stored line. The memory lasts until the extension host restarts. Remedy, **tested once (user, 2026-11-25):** close the custom-editor preview tab of the file, run `Developer: Restart Extension Host`; the text view then stayed in place, and `Markdown: Open Preview` did not bring the problem back. A Claude Code chat kept running across the restart and only lost its IDE connection. Whether open files, terminals and sign-in all survived was not reported either way. `Ctrl+Shift+V` (`markdown.togglePreview`) reopens the file in the custom-editor preview (read in the 1.148.0 code, not run).
  - **Why `Open Preview` loses the old file (user's report 2026-11-25; mechanism read in the 1.148.0 code):** an unlocked dynamic preview listens to `onDidChangeActiveTextEditor` and, when another Markdown text file becomes active, disposes its content and renders that file at the text view's first visible line. Returning through the old plain file therefore starts where that text view is, often the top. `Markdown: Toggle Preview Locking` stops the following (read in code, not tested). By the same code, a preview created with a starting line and later scrolled drops its saved scroll when its tab is hidden and shown again; not tested either.
  - **Per-file rendered tabs (tested 2026-11-25, 1.148.0, one machine, throwaway profile without extensions, two generated files, driven over the DevTools protocol, scroll offset read before and after):** with the two settings above, file A left at a chosen mid-file heading and file B at another, each came back to the same pixel after switching through the file list, and A also through its tab. A file edited on disk while its tab was hidden came back 16 px lower (one line). `draft.md` opened as plain text. With the association alone and preview tabs left on, the next single click replaced the tab and the position was lost (came back at the top), so both settings are needed. The control runs meant to reproduce the `Open Preview` symptom and test locking are **not valid**: the command typed in the palette may have run a different command. Not tested: a window reload, links with a `#fragment`, the user's own profile.
  - The reverse, the preview moving with the text editor, goes through `scrollPreviewWithEditor` (default true); a likely cause of the preview jumping, **not tested**. Side by side, scrolling either view moved the other (reported by the user; both settings default to true).
  - **A fix that worked once (anecdotal: one user, one machine, 2026-11-25; found by testing, not from a source):** the view returned to a fixed line in every file, in the text editor and not only the preview. It still did so with `--disable-extensions` and with no change to the file on disk. A clean profile (`code --user-data-dir <dir> --extensions-dir <dir2>`) kept the position, also with the user's `settings.json` copied in. With VS Code closed, renaming that workspace's folder under `%APPDATA%/Code/User/workspaceStorage/<hash>` to `<hash>-backup` (VS Code then makes a fresh one) fixed it. The symptom came back the same day. **Cost, reported by the user:** open files, terminals and account sign-in of that window are lost, so do not suggest it first. The earlier conclusion, that the saved workspace state was the cause, is withdrawn: the rename also restarted VS Code, which empties the memory described above. (inference: findings/vscode-markdown-scroll-position-lost)
  - No published source found that gives a fix for the plain text editor (searched on 1.147.0). No bug report matching the symptom was found for the text editor on 1.147.
