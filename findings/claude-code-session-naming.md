# Claude Code session names, auto titles and task descriptions

- **Question:** How does Claude Code name sessions (auto title, /rename, the `sessionTitle` hook field), is there a per-session task description other sessions can read, and what naming does the documentation advise when several sessions run at once?
- **Finding:**
  - *Auto title.* An unnamed session gets a short title generated from the first prompt by a background request to a small model; `claude -p` runs from a script get none. The docs say a generated title "isn't a custom title", so a name set with `/rename`, `-n` or `Ctrl+R` is not replaced by it. (Documentation, read through a docs-agent summary.)
  - *Hook field.* `sessionTitle` in SessionStart or UserPromptSubmit hook output "sets the session title, with the same effect as `/rename`"; both events receive the current `session_title`, and the docs advise checking it first so a user's name is not overwritten. The docs do not say outright that a hook title overrides the generated one, nor where it shows in listings; "same effect as `/rename`" implies both.
  - *No settable description.* The agent view shows a one-line summary per session, generated by Claude Code from the session's output (refreshed at most every 15 seconds while working) and a state (Working, Needs input, Idle, Completed, Failed, Stopped). `claude agents --json` exposes `name` and `state`, no summary. No documented field lets a session set its own description; the docs advise against writing the job state files. So the title is the only settable label other sessions can see. Whether a session can run `/rename` itself is not documented.
  - *Naming advice.* "Give sessions descriptive names ... This matters most when you're working on several tasks in parallel." Duplicate names are numbered; no convention beyond "descriptive".
  - *Auto titles in practice (user reports).* GitHub issues describe generated titles as often short, generic or picking up fragments of the conversation, and several report a `/rename` name later replaced by a generated title (also after context compaction). Reports, not tested here, and the behaviour may have changed since.
  - *Reading for a multi-chat setup (inference, not a source claim):* a title that carries both the repository and the task serves parallel chats best; the generated title gives the task but not the repository, a repository-only title gives the place but not the task, and a hook sees only the first prompt and the launch folder.
- **Evidence strength:** *common practice* for the documented behaviour (official docs); *anecdotal* for the overwrite and quality complaints (issue reports).
