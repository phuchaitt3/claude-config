# Keeping a long agent run from piling every task into one context

- **Question:** When one agent works through many tasks in a row (a self-paced loop, an overnight run), how do practitioners stop its context, and so its token cost, growing with every task? Subagents, a fresh session per task, or a handoff to other chats?

- **Finding:**
  - **The cost grows with context length.** Every request re-sends the whole conversation, so a session that has finished N tasks pays for all N on each turn of the next one (Claude Code best practices; see `findings/claude-code-clear-vs-compact`). Quality also drops as old output, dead ends and stale reasoning pile up ("context rot"; practitioner reports, no controlled study found).
  - **Standard pattern: a thin outer loop, a fresh context per task, and state kept in files.** Anthropic's long-running harness runs each coding session in a new context window ("each new session begins with no memory of what came before"). Continuity lives in artifacts: a JSON feature list with a pass/fail field, a progress log, and git history with descriptive commits. Each session reads them, takes one feature, tests it, commits and updates the log. The post says compaction "isn't sufficient" on its own, because it "doesn't always pass perfectly clear instructions to the next agent" (official engineering post). The community "Ralph" loop is the same idea: a shell loop starts a new `claude -p` per iteration, with the task list and notes on disk. Guides describe it as trading some extra tokens for avoiding compaction and context rot (practitioner sources).
  - **Subagents isolate bulky work, but the parent still grows.** Claude Code docs: use a subagent when "the task produces verbose output you don't need in your main context" and "the work is self-contained and can return a summary". Stay in the main conversation when "multiple phases share significant context, such as planning, implementation, and testing", or the change is quick. Subagents count toward the same usage limits, and their results return to the parent, so many detailed results still fill it. A subagent can run on a cheaper model through the `model` field (official docs). One practitioner postmortem found that orchestrator context pollution, not parallelism, was the main cost, and fixed it by having workers return short summaries (anecdotal).
  - **More agents cost more tokens; they do not save them.** Anthropic measured agents at about 4x the tokens of chat and multi-agent systems at about 15x. Multi-agent setups pay off only for high-value, parallelisable work. They fit poorly when agents must share context or depend on each other, and "most coding tasks involve fewer truly parallelizable tasks than research" (official engineering post). Claude Code agent teams (experimental) "use significantly more tokens than a single session", and token use scales linearly with teammates. The docs suggest 3-5 teammates and 5-6 tasks each, and say that for "routine tasks, a single session is more cost-effective" (official docs).
  - **Cache detail.** Subagent and in-process teammate requests use a 5-minute prompt cache by default, against the main conversation's longer one (`subagentPromptCacheTtl` raises it). Each new session or subagent also pays its own startup load (CLAUDE.md, skill listing, tools) (official docs).
  - **Checker's inference for a self-paced loop:** the cheap change is to make each task a fresh context and keep the loop itself thin. The loop session only picks the next issue, claims it, and dispatches one worker per task (a subagent in its own worktree that returns a few lines, or a fresh `claude -p` / new chat). The issue, branch, PR and handoff files carry the state, which this setup already keeps on GitHub. A task's own phases (plan, implement, test) stay in one worker's context, as the docs advise. Running several workers at once is a separate decision: it raises total tokens and is worth it only for independent tasks. No source measured fresh-context-per-task against one long session on the same backlog, so a local before/after count (tokens per merged PR from the transcripts) is the way to check it.

  - Which kind of worker gets which task (a subagent or a new session) and how many run at once: see `findings/agent-delegation-choice`.

- **Evidence strength:** *official standard* for subagent and agent-team guidance, token multipliers and cache behaviour (Anthropic docs and engineering posts). *Vendor or single source* for the fresh-session-per-task harness (one Anthropic post, tested on full-stack web apps). *Anecdotal* for context rot and Ralph-loop cost trade-offs (practitioner blogs, no measurements).
