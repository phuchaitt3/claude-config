# Freeing disk space

Added 2026-11-15 (user's decision) after a chat walked a 238 GB drive with a PowerShell loop for over 15 minutes, where an MFT-reading analyzer takes seconds. Extended the same day after a cleanup that took C: from 19 GB to 44 GB free. (standard: findings/disk-cleanup-windows, findings/uv-cache-management, findings/cache-location-windows, checked 2026-11-15)

1. **Measure, never walk.** Never scan a whole drive with `Get-ChildItem -Recurse`, `du` or a folder loop: it takes minutes and slows every chat. Run `schtasks /Run /TN WizTreeExport`, wait until `$env:ProgramData\WizTreeExport\C.csv` has a new write time (about 20 s; the file is locked while it is written, so retry a read that fails), and read the folder rows (names end in `\`, the second column is bytes): skip the two header lines, `ConvertFrom-Csv -Header Name,Size,Alloc,Mod,Attr,Files,Folders`, sort by Size. Walking one known small folder is fine. If the task does not exist, ask the user to run WizTree themselves, or to run `~/claude-config/scripts/wiztree_task_setup.ps1 -Source <WizTree folder>` once in an administrator PowerShell, which sets the task up so no later run needs a prompt.
2. **Report** the top items to the user: size, what each is, and its group: Windows, developer caches, Docker, apps, user data. Then offer the cleanup candidates in one `AskUserQuestion` (multi-select, each with its size and command), because one list gets one answer.
3. **Delete nothing without the user's yes for that item.** The yes covers what was listed: re-check before deleting, and if a thing differs from what you listed, stop and say so.
   - **Developer caches:** clean with the tool's own command (`uv cache prune`, `pip cache purge`, `pnpm store prune`, `npm cache verify`), never by deleting the folder. Do not clean a cache on a schedule (it refills and the next install pays again); clean when space is short. A Hugging Face model folder under `hub\` may be deleted by hand, one at a time, after checking the same model exists, with the same size, in the cache you keep.
   - **Move, don't keep cleaning:** a cache that a tool lets you redirect belongs beside the projects that use it (`UV_CACHE_DIR`, `HF_HOME`, `PIP_CACHE_DIR`, `npm_config_cache`; user level via `[Environment]::SetEnvironmentVariable(name, value, 'User')`). Check what is already set first (`[Environment]::GetEnvironmentVariable(name,'User')`): a cache that keeps refilling on C: usually has the variable set already, but a process started before it. Tell the user to restart VS Code. A variable does not move the old cache: move its contents (`robocopy <old> <new> /E /MOVE`) or clean it with the tool's `--cache-dir <old>` option. Check what kind of disk the target is (`Get-Partition -DriveLetter D | Get-Disk`): a hard disk is slower than the SSD.
   - **App caches (browser, music player):** the user clears them from the app's own settings; do not move or junction them.
   - **Docker:** through `workflow:docker`. `docker image prune` finds nothing when images are tagged; per-task compose images (`<task>-api`, `-worker`, `-migrate`) from finished tasks are the usual several GB: list them, get the yes, `docker rmi` those only, keep base images the next run needs (embedding server, database, vector store, object store), then `docker builder prune -f` twice (the second removes layers the first still needed). The disk file compacts by less than the space freed inside it (5 of 11 GB in the test).
   - **Logs:** list the folder's files with dates and sizes before deleting; delete files, not the folder.
   - **Windows:** `Dism /Online /Cleanup-Image /AnalyzeComponentStore` is read-only but needs an administrator prompt: run it with `Start-Process powershell -Verb RunAs -Wait`, writing to a file in the scratchpad, and tell the user to accept the prompt. If it says cleanup is recommended, `/StartComponentCleanup` needs its own yes, takes 10 to 20 minutes, and is safe beside other work but not during a long benchmark or a Windows update. Never `/ResetBase`.
   - Never: Docker volumes, credential files, anything not identified, `docker system prune -a --volumes`.
4. **Log the outcome** (date, what was removed, GB freed, free space after) where the user keeps machine notes (a `machine/disk-c-cleanup.md` page in their notes repo holds the quick-check commands, what takes space and the log), so the next cleanup starts from it. A chat that finds a new big item adds it to that page's table.
5. **Tell the user** the one thing they must do afterwards (restart VS Code after a cache variable changed) and the free space reached against the target: 30 GB or more for an overnight run, because the overnight loop skips large downloads under 20 GB.
