# Freeing disk space

Added 2026-11-15 (user's decision) after a chat walked a 238 GB drive with a PowerShell loop for over 15 minutes, where an MFT-reading analyzer takes seconds. Extended the same day after a cleanup that took C: from 19 GB to 44 GB free. (standard: findings/disk-cleanup-windows, findings/uv-cache-management, findings/cache-location-windows, checked 2026-11-15)

0. **Reuse the last check** (user's decision, 2026-11-24, so a repeat cleanup goes straight to cleaning): every measure (step 1) saves its ranked report to `~/.claude/disk-checks/<drive>-<YYYY-MM-DD>.md` (local, never committed: it names the user's apps). Before measuring, read the newest report for that drive. Reuse it, skipping WizTree, when it is 7 days old or less AND the user says nothing was installed since, or the newest `InstallDate` in the Windows Uninstall registry keys is older than the report; say "reusing the check of <date>" and go straight to step 2. Measure again when the report is older, an install is likely, or free space has fallen more than 5 GB since the report. Reusing never replaces the re-check before each delete (step 3). Each cleanup appends what was removed and the free space after to the same file.
1. **Measure, never walk.** Never scan a whole drive with `Get-ChildItem -Recurse`, `du` or a folder loop: it takes minutes and slows every chat. Run `schtasks /Run /TN WizTreeExport`, wait until `$env:ProgramData\WizTreeExport\C.csv` has a new write time (about 20 s; the file is locked while it is written, so retry a read that fails), and read the folder rows (names end in `\`, the second column is bytes): skip the two header lines, `ConvertFrom-Csv -Header Name,Size,Alloc,Mod,Attr,Files,Folders`, sort by Size. Walking one known small folder is fine. If the task does not exist, ask the user to run WizTree themselves, or to run `~/claude-config/scripts/wiztree_task_setup.ps1 -Source <WizTree folder>` once in an administrator PowerShell, which sets the task up so no later run needs a prompt. WizTree may be a normal install in any folder (not only under Program Files): look for `WizTree64.exe` where the user says, do not conclude it is missing from a search of the usual folders. The setup script copies that folder, so re-run it after a WizTree update. In Git Bash, `schtasks /Run` is rewritten as a path and fails: run it from PowerShell (or set `MSYS_NO_PATHCONV=1`).
1b. **List unused apps and leftovers** (user's decision, 2026-11-27, after a cleanup offered caches and skipped apps): before offering anything, list installed apps (the three registry Uninstall keys and Store apps), measure their install and data folders on C: (the registry size is often blank), and match each to its last launch in UserAssist. UserAssist misses command-line, service and background use, so "no launch seen" is not "unused": the user decides. Also look for leftovers (data of removed apps, game folders no Steam manifest lists, C:\Windows\LiveKernelReports). Do this even when WizTree fails; never offer a cache-only list.
2. **Report** the top items to the user: size, what each is, and its group: Windows, developer caches, Docker, apps, user data. Then offer the cleanup candidates in one `AskUserQuestion` (multi-select, each with its size and command), because one list gets one answer. Offer lasting items first (unused apps, models, installers, old downloads, finished tasks' images), then caches that can move to another drive, last caches that refill; mark each item "lasting" or "refills" (user's decision, 2026-11-26; standard: findings/disk-cleanup-windows, checked 2026-11-24).
3. **Delete nothing without the user's yes for that item.** The yes covers what was listed: re-check before deleting, and if a thing differs from what you listed, stop and say so. If the harness blocks a delete as a protected path, give the user the command or the app steps; do not try another way (user's decision, 2026-11-26).
   - **Developer caches:** clean with the tool's own command (`uv cache prune`, `pip cache purge`, `pnpm store prune`, `npm cache verify`), never by deleting the folder. Do not clean a cache on a schedule (it refills and the next install pays again); clean when space is short (standard: findings/uv-cache-management, checked 2026-11-23). **Standing yes** (user's decision, 2026-11-23): when C: has under 15 GB free, a chat may run `pip cache purge` and `uv cache prune` without asking, not while an install or sync is running, and says in its next reply how many GB it freed (measure free space before and after). Every other item in this list still needs a yes. A Hugging Face model folder under `hub\` may be deleted by hand, one at a time, after checking the same model exists, with the same size, in the cache you keep.
   - **Move, don't keep cleaning:** a cache that a tool lets you redirect belongs beside the projects that use it (`UV_CACHE_DIR`, `HF_HOME`, `PIP_CACHE_DIR`, `npm_config_cache`; user level via `[Environment]::SetEnvironmentVariable(name, value, 'User')`). Check what is already set first (`[Environment]::GetEnvironmentVariable(name,'User')`): a cache that keeps refilling on C: usually has the variable set already, but a process started before it. Tell the user to restart VS Code. A variable does not move the old cache: move its contents (`robocopy <old> <new> /E /MOVE`) or clean it with the tool's `--cache-dir <old>` option. Check what kind of disk the target is (`Get-Partition -DriveLetter D | Get-Disk`): a hard disk is slower than the SSD. Measure two SSDs too, do not assume: on the desktop PC (2026-11-23) both drives were SATA SSDs, but C: wrote 1 GB sequentially at about 340 MB/s and D: at about 120 MB/s (random 4K writes were equal), and D: was the smaller, fuller drive, so moving pip and uv caches there gained nothing. Compare free space as well as speed before proposing a move. One real gain: uv cannot hardlink across drives, so a venv on D: with the uv cache on C: is a full copy; if the venvs live on D: and D: has room, `UV_CACHE_DIR` on D: avoids that.
   - **App caches (browser, music player):** the user clears them from the app's own settings; do not move or junction them.
   - **Docker:** through `workflow:docker`. `docker image prune` finds nothing when images are tagged; per-task compose images (`<task>-api`, `-worker`, `-migrate`) from finished tasks are the usual several GB: list them, get the yes, `docker rmi` those only, keep base images the next run needs (embedding server, database, vector store, object store), then `docker builder prune -f` twice (the second removes layers the first still needed). The disk file compacts by less than the space freed inside it (5 of 11 GB in the test). The other direction: building a Compose stack's images (`up -d` with `build:` services; one Python plus Node project with an apt install) wrote about 8 GB to C: in four minutes, well over the 2-4 GB guessed. Before such a build, check free space on C: and watch it during the build; stop below 10 GB free.
   - **Logs:** list the folder's files with dates and sizes before deleting; delete files, not the folder.
   - **Windows:** `Dism /Online /Cleanup-Image /AnalyzeComponentStore` is read-only but needs an administrator prompt: run it with `Start-Process powershell -Verb RunAs -Wait`, writing to a file in the scratchpad, and tell the user to accept the prompt. If it says cleanup is recommended, `/StartComponentCleanup` needs its own yes, takes 10 to 20 minutes, and is safe beside other work but not during a long benchmark or a Windows update. Never `/ResetBase`.
   - Never: Docker volumes, credential files, anything not identified, `docker system prune -a --volumes`.
4. **Log the outcome** (date, what was removed, GB freed, free space after) where the user keeps machine notes (a `machine/disk-c-cleanup.md` page in their notes repo holds the quick-check commands, what takes space and the log), so the next cleanup starts from it. A chat that finds a new big item adds it to that page's table.
5. **Tell the user** the one thing they must do afterwards (restart VS Code after a cache variable changed) and the free space reached against the target: 30 GB or more for an overnight run, because the overnight loop skips large downloads under 20 GB.
