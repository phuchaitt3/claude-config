# Self-driving chat

(User's decision, 2026-10-31: per chat, started by the user's prompt only; saved globally so any project can use it. Standard: Kanban pull system, where a worker takes the next ready item when it has capacity, with a WIP limit; checked 2026-10-31.)

A chat never starts this by itself. The user starts it in a chat by asking, and it lasts until that chat ends or the user says stop. It does not change any project limit: a project's `CLAUDE.md` hard limits, user-merge paths and queue limits all still apply.

## Start

Invoke the `loop` skill (Skill tool, skill `loop`) with no interval (the model paces itself) and this brief as its prompt. Running the brief once in the current turn is not a loop: the run then ends with that turn (user's decision, 2026-11-14, after an overnight run did exactly that and stopped after 2 minutes). If the project uses the `workflow:multi-chat` protocol, load that skill first and follow its claim rules. When the user asks how to start, watch or stop an overnight run, walk them through `START-OVERNIGHT.md` in this skill's folder.

> Each round:
> 1. Sync: run `python <this skill's folder>/next_task.py --status` in the repository (add `--handoff <path>` if the project has a handoff repo). It pulls the handoff repo if given and prints, in one output, open PRs, claimed issues, worktrees and the startable issues. If it prints `STALE CLAIM? #n: ...` (the best claimed issue outranks every startable one and its claim fails the claim sweep's test), run `python <plugin>/hooks/claim_sweep.py sweep <main checkout>` at once instead of waiting for the hourly sweep, then re-run the sync (user's decision, 2026-11-18, #25). Use that output for steps 2 and 3; do not repeat those checks with separate `gh` or `git` calls in the same round (user's decision, 2026-11-14: each loop-chat call re-reads its whole context, and status checks were most of its calls).
> 2. **Review first** (only in review mode `peer`; in other modes merge your own PRs as that mode says, see `workflow:pr-review`, "Review modes"). Take the oldest open PR with no review comment from a chat other than its author and review it as `workflow:pr-review` says. Never review your own PR.
> 3. **Then work.** Run `python <this skill's folder>/next_task.py` in the repository (in overnight mode add `--log-picks`, which appends the ranking, the labels it saw and any heavy skip to `~/.claude/overnight-picks.jsonl`; once the round has chosen, run `python <this skill's folder>/picks_log.py taken --issue <n>` with `--skip <m>=<reason>` for each higher-ranked issue passed over for a reason other than a HEAVY HOLD; local, never committed; `picks_log.py report` prints, per night, the share of picks that were the top-ranked startable issue and the reasons for the rest; user's decision, 2026-11-18, #27). It lists the startable issues `priority:first` first (the user's override, 2026-11-17: ahead of resume work; only the user sets it), then resume-first, then bottleneck-first (its docstring holds the order: issues labelled `resume:1`–`resume:6` by the triage pass in `TRIAGE.md` and the issues that unblock them, then `priority:now` and bottlenecks, then the other priority labels; user's decision, 2026-11-15); take the first one the rules below let you take (check `main` and the issue for existing work, such as a design brief, code or a ticked box, before routing; a task already done is closed out, by ticking the box and releasing the claim, not redone; user's decision, 2026-11-14, after three workers were routed to work that already existed), and honour a `HEAVY HOLD:` line it prints ("Heavy-task hold" below), and make the `fix:` lines it prints (a missing dependency link or `priority:now` label) on the way. If it cannot reach GitHub, take `priority:now`, else the oldest unblocked `priority:next`, else the oldest unblocked `priority:later`. Claim it as the project says (label plus a comment listing the files) and verify the claim. Then route it, so the loop chat's context stays small (user's decision, 2026-11-14; standard: findings/long-agent-run-context and findings/agent-delegation-choice, checked 2026-11-14):
>    - (a) a short task with a checkable finish goes to one worker subagent (`workflow:subagents` applies; starting self-drive is the user's ask): `isolation: "worktree"`, Sonnet unless the issue's tag names Opus, a tight brief (issue number, files, the check to run, any GPU-lock command), a report of at most 10 lines (PR link, files changed, checks with results, open questions). The worker runs lint and tests, commits, pushes its branch and opens the PR with `Closes #n`. The loop chat does not read the diff or any log; it verifies from small sources: `gh pr checks`, `gh pr diff --stat` (the file list matches the brief and no user-merge path is touched unless intended) and the PR body's closing line. A finished Kaggle run goes to a worker with the run id; the loop chat never opens its log or output. On a user-merge path, or when the report and `--stat` disagree, the loop chat reads the diff itself (user's decision, 2026-11-14; standard: findings/agent-worker-scope-and-verification, checked 2026-11-14). A worker may take up to 3 small issues in a row when each is in the same repository, touches files no other claim holds, and has its own checkable finish; the loop claims each before dispatch, the worker opens one PR per issue, and its report lists each PR (at most 10 lines in all). (User's decision, 2026-11-14. Why: each worker pays about 45K tokens of startup context before any work; measured 2026-11-14.);
>    - (b) a long task (a measurement run, about an hour or more) goes to a background session: `claude --bg -n <issue>-<slug> "<brief>"` from the main checkout (on a machine without `claude` on PATH, the VS Code extension's bundled `claude.exe`). It works in its own worktree and opens its own PR; the loop chat reads only the PR and `claude agents --json` state. The brief says: create the worktree with `git worktree add ../<ID>-<slug>` (never `EnterWorktree` or `--worktree`), pass the PR body as `--body-file` (never `--body -`), and finish with `gh pr view <n> --json closingIssuesReferences`. When the worker is done, the loop chat checks that the PR body has `Closes #n` (fixing it if not), removes the session with `claude rm <id>`, and checks `git worktree list` for a stray worktree under `main/.claude/worktrees` (first real run, 2026-11-14, hit all three: a stray locked worktree, a PR body of just `-`, and a finished session left running). While a background session works, the loop chat starts a background Bash command that polls every 60 s until the worker's PR is open or its session has ended (`gh pr list --head <branch>`, `claude agents --json`), so the harness re-invokes the loop when the worker finishes; the round still ends with `ScheduleWakeup` (1200 s or more) as a fallback (user's decision, 2026-11-14, after fixed 25-minute wakeups left 10 to 19 minutes idle at each of four handoffs in one run);
>    - (c) a task done in a couple of tool calls stays in the loop chat.
>    - **Measurement briefs:** a worker brief for a measurement fixes, before any held-out result is seen, the metric, the threshold or exit rule, and which items are held out (`workflow:experiment` step 1). A rule changed after a held-out result is seen makes that result exploratory: the PR, the doc and any README line say so and do not report it as held-out. An LLM judge is not the model whose answers it grades; when no other model fits on the machine, the judged results are exploratory too (user's decision, 2026-11-14, after an overnight worker loosened its threshold after seeing the blind result, and a judge graded its own model's answers).
>    One worker at a time. Then start the next round.
> 4. **Route or skip** an issue:
>    - needs an architecture or design choice: write a brief in the project's design folder, open it as a PR, move on;
>    - touches a path the project reserves for the user (the project's `CLAUDE.md` lists them; in solo-fast by default infra, deploy config, secrets, money, lockfiles by risk, and a `.claude/` change that loosens a guard, see `workflow:pr-review`): do the work and open the PR with `needs-you` and the user as reviewer; the gate is the merge, not the work, and there is no limit on how many such PRs wait (user's decision, 2026-11-17: no limit on items waiting for the user, so human review never slows the work; findings/human-approval-queue-limits);
>    - needs a measurement, GPU or free-quota cloud run (Kaggle): in overnight mode, run it (local GPU through `gpu_run.py run --wait` with an `# estimate:`; a cloud run with the project's own runner, waiting on it in the background, not polling); in daytime self-drive, skip it (user's decision, 2026-11-14; the free-cloud exception is in the working rules' Hard limits);
>    - skip (leave it, say nothing more) only when it: carries `needs-you`; needs a decision only the user can make; involves secrets; calls a paid API at scale; overlaps a file another chat has claimed; or needs a tool the machine lacks, or (in daytime) a large download, or in overnight mode a download that needs money or does not fit on disk. **Flag every skip that waits on the user** (user's decision, 2026-11-17, after overnight runs skipped the top-ranked user-blocked issues for two nights with only a line in the morning summary): when a round skips an issue because it needs the user's decision, approval or money, add `needs-you` to it with the user as assignee in the same round (or file one issue per decision), unless it already carries `needs-you`. Add a comment with what is blocked, the exact action, the time it takes, and what happens if nothing is done; a paid step names an estimated cost. In a public repository the comment holds no private detail ("private item; ask in chat"). The morning summary lists every open `needs-you` item in the repository under "blocked on you", oldest first, each with its age in days (`gh issue list --label needs-you --json number,title,createdAt`, one query per repository the run touched), so an item left for days stands out without any limit on how many wait (user's decision, 2026-11-17). A skip for any other reason (secrets, a file claimed by another chat, a missing tool) is not flagged (no limit applies to how many items wait for the user; the user's agents help review them, so the work never waits for human review);
>    - (overnight mode only) a free large download (model weights, a Docker image) is allowed once free disk space is checked (keep at least 20 GB free on the system drive); a free-tier deploy and creating a new repository are allowed under the working rules' overnight exceptions; skip only when the step needs money, a credential the agent may not read, or does not fit on disk (user's decision, 2026-11-14).
> 5. **Stop** the loop (do not schedule another round) when: no issue is left that steps 3 and 4 can take (daytime only; in overnight mode the loop files new issues instead, see "New issues" below); three different tasks in a row each fail CI twice (a likely shared cause; say so); or you are unsure the task is yours. A task whose CI fails twice is parked, not retried: leave its PR as a draft, remove `needs-you`, label the PR (or issue) `parked` (create the label if missing), post one comment saying what unblocks it (for example "needs Docker", "needs main merged in") and the untried fix, record the same in the summary, and take the next eligible task. At the start of every round, before step 3, re-check each open `parked` item (`gh pr list --label parked`, `gh issue list --label parked`): if its unblock condition now holds, resume it as the round's task; if it has been parked more than 2 days, file a `needs-you` issue for it (what is stuck, the exact action, what happens if nothing is done) and say so in the summary, rather than leaving it for a later round to notice (user's decision, 2026-11-15, after a parked draft PR sat for hours with no label, owner or resume condition) (user's decision, 2026-11-14; standard: findings/agent-loop-stop-on-repeated-failure, checked 2026-11-14). Before stopping, run `next_task.py --limit 100` and list every issue it prints with the step-4 bullet that rules it out; an issue that needs an architecture or design choice is not ruled out: write the brief and open it as a PR. "Lower priority", "did not read it" and "touches `.github/`" match no bullet, so take the issue (user's decision, 2026-11-14). Before the loop ends for any reason, release every claim it or its workers hold and comment what is done, what is left and how to resume (`workflow:multi-chat-repo`, "Release on stop"; user's decision, 2026-11-18). Never ask the user what to do next; say why it stopped in one line (user's decision, 2026-10-31; standard: bounded autonomy, where an agent escalates only at the edge of its authority and halts on explicit stop conditions, and Kanban pull of the next ready item; checked 2026-10-31).
> 6. Between rounds say nothing unless something blocks the user. When the loop stops, give one line: what was done (PR links) and why it stopped.
> 7. **End every turn with `ScheduleWakeup`**: the last tool call of a round is `ScheduleWakeup` with this same prompt (a delay of 60 seconds or more), or `stop: true` when step 5 says to stop. Since Claude Code 2.1.319 a turn that ends with neither ends the loop at once, with no fallback wakeup, and nothing tells the user. This holds after a turn that waits on a background session or a GPU job too (user's decision, 2026-11-14; standard: findings/overnight-agent-runs, checked 2026-11-14) A `Stop` hook (`loop_guard.py`) backs this rule: when a turn ends with no wakeup pending and no background task running, it tells you to schedule or stop, once per turn (user's decision, 2026-11-14; standard: findings/agent-loop-control-enforcement, checked 2026-11-14).
> 7a. **Context reset (overnight mode only).** In overnight mode, also write a 3-line resume note (round number, open PRs and claimed issue, what the next round starts with) to the morning-summary file at the end of every round, so a restarted chat or a successor can pick up the loop (user's decision, 2026-11-14). At the end of every round, whatever ended it (a PR opened, reviewed or merged, a task parked, a Kaggle wait started), run `python <this skill's folder>/context_size.py --log` with no session ID (it reads `CLAUDE_CODE_SESSION_ID`; never pass the six-character `ListAgents` ID, which on 2026-11-15 made every check fail and let a loop run on past 210K). A non-zero exit means the check did not run: say so in the morning summary rather than carry on as if under the limit. If it prints more than 150000, write the resume note (round number, open PRs, claimed issue, what the next round starts with) to the morning-summary file, start the successor with `claude --bg -n selfdrive-<n> '<this brief>; resume note: <path>'` from the main checkout, confirm it appears in `claude agents --json`, and only then end this chat with `ScheduleWakeup` `stop: true`. If the successor does not appear, keep going in this chat and say so in the summary. A `PreToolUse` hook (`context_guard.py`) on `ScheduleWakeup` reads the chat's context at every round end and reminds you when it is over 150000, so a round that ended in a way this list missed is still caught; it does not replace running the check (user's decision, 2026-11-15, after a round ended in a merge, skipped the check, and the chat ran on to 170K). **A worker still running** when the check reads over the limit delays the handover, but only for a while: from then on start no new task, worker or background session, finish and merge or park what is in flight, write the time of the first reading over the limit to the morning-summary file, and hand over at the latest 60 minutes after it, releasing the claim on any task the worker has not finished and naming it as unfinished in the resume note. A task expected to take more than about 10 minutes goes to a worker started as its own background session (`claude --bg`) that opens its own PR, which survives a handover; a subagent is for short tasks, because its result returns only to this chat (user's decision, 2026-11-15, after a chat held over 150K waiting for a subagent with no end point; the 60 minutes is a starting guess, not a sourced figure). The successor's first round reads the note and the morning-summary file. Never run two loop sessions at once (user's decision, 2026-11-14; standard: findings/agent-session-handoff-reset, checked 2026-11-14; the threshold is a local measurement, not a sourced figure). **Threshold trial** (user's decision, 2026-11-15): 150K replaces 200K for now. On 21 past overnight sessions the cost model f(T) = r(F+T)/2 + Rg/(T−F) (start context F ≈ 55K, growth g ≈ 1.8K per turn, restart cost R ≈ 260K weighted units, cache-read weight r = 0.1) has its minimum at T* ≈ 151K, about 3% cheaper per turn than 200K; tool-error rates showed no rise with context. `--log` appends each round's session statistics and the 5-hour quota to `~/.claude/context-threshold-log.jsonl` (local; transcripts are deleted after 30 days, so this log is the record; the 21 sessions are backfilled at threshold 200000). `python <this skill's folder>/context_report.py` summarises it by threshold and recomputes T*; `context_report.py --prs` joins sessions to the PRs opened and merged in their windows (the log line names the repo). Assess after about two weeks of overnight runs, and go back to 200K if the cost per turn or the PRs merged per session get worse.
> 7b. **Quota pause.** When the `quota_watch` hook says the 5-hour usage is at or above its threshold (90%), start no new worker, background session or long step; let a running worker finish. Start the `sleep <seconds>` it names as a background command (it keeps the machine awake through the wait and wakes the loop after the reset), and end the round with `ScheduleWakeup` at the delay it names (at most 3600 s). Each wakeup during the pause only checks the quota and reschedules. After the reset, check each worker started before the pause (`claude agents --json`, its PR); one stopped by the limit is resumed with `SendMessage` (a subagent) or a message to its session, then normal rounds go on. Record each pause (start, reset, resume) in the morning summary. Built-in auto-continue (`autoContinueAtUsageLimit`) stays on as the fallback. Why: a wakeup or worker report that fires into a live limit counts as a repeated hit and stops auto-continue, and a laptop asleep for more than 30 minutes at the reset waits for Enter; both stalled one overnight run for 1.5 to 2.3 hours after each reset (user's decision, 2026-11-14; standard: findings/claude-code-usage-limit-resume, checked 2026-11-14; the 90% threshold is a starting guess, not a sourced figure: tune it from the pauses recorded).

## Pacing

After opening a PR, start the next round at once in a new worktree; do not wait for its review or CI (user's decision, 2026-10-31; standard: Kanban pull with a WIP limit on review, about 1-2 items per reviewer, and background coding agents such as Copilot coding agent open a PR and move on; checked 2026-10-31). Wait only when:

- 2 of your own PRs are open with no review yet (review mode `peer` only): review others' PRs, or schedule the next round in 5 to 10 minutes;
- the next eligible task depends on an open PR's change.

When nothing is eligible, stop rather than poll (overnight mode files new issues instead, see "Overnight mode"). Never schedule waits shorter than 60 seconds.

## Stopping

The user stops it by telling the chat to stop. The chat then ends the loop and finishes or parks its current task (commit as `wip:` on its own branch if unfinished).

## Overnight mode (user's decision, 2026-11-13)

The user starts it by asking a chat to "self-drive overnight". It is the loop above with the extra rules below. The project's merge mode and user-merge paths still apply, so a solo-fast project merges after its usual check. There is no cap on PRs, rounds or hours: the loop ends when three different tasks in a row each fail CI twice, or the user stops it (Esc while the chat waits; otherwise tell it to stop). (Departs from standard: findings/overnight-agent-runs recommends caps on iterations, spend and time; the user chose none, relying on the harness suspending a chat at its usage limit, 2026-11-13.)

**Before the first round**, check what you can and say in one line what the user must do: `gh auth status` shows the bot, the working tree is clean, the `keep-awake` status line shows a hold. Usage credits must be off (the user checks at claude.ai/settings/usage; you cannot see it), so a usage limit pauses the run instead of billing it. Never turn on usage or API credits. That one line names the keep-awake hold you saw, or says none is shown. Then record where `main` stands: run `git fetch`, then create the morning summary file at once with one line, `Start: <output of git rev-parse origin/main> (<repo>, <date and time>)`, so the starting commit survives a crash or a context reset (user's decision, 2026-11-14). Also tell the user to start Claude Code for an overnight run with `CLAUDE_CODE_LOOP_KEEPALIVE=1` set (read at startup; you cannot set it for a chat already open): it restores one fallback wakeup about 20 minutes after a turn that forgot step 7, a safety net and not a substitute (standard: findings/overnight-agent-runs, checked 2026-11-14). Start the overnight loop as a background session (`claude --bg -n selfdrive-<date> '<brief>'` with the extension's bundled `claude.exe`, from the repository folder, `CLAUDE_CODE_LOOP_KEEPALIVE=1` set in that shell), not in the VS Code panel: a pending `ScheduleWakeup` lives in the session's process, so an extension reload or update drops it, while a background session's wakeup fired across a reload (tested 2026-11-14, Claude Code 2.1.325). A background session also runs the status line with the quota figures, so the quota pause (step 7b) works there (tested the same day). If a panel chat is restarted mid-loop anyway, the `loop_guard` hook tells it at its next turn to re-arm (user's decision, 2026-11-14).

**Resume triage** (user's decision, 2026-11-15). Before the first round, in each repository the run works in, dispatch one worker (Opus, medium effort, as `TRIAGE.md` says) with `TRIAGE.md` in this skill's folder: it labels the open issues that do not yet carry a `resume:` label, so `next_task.py` ranks resume work first. Skip it when `~/.claude/resume-gaps.md` is absent or the project's `CLAUDE.md` says "no gap list". Issues the run files itself get their `resume:` and `gap:` labels when filed, by the same table.

**Temperature log** (user's decision, 2026-11-14; always-on task, 2026-11-17, after chat-started loggers died at 20:58 and 00:21 on two nights). The thermal logger runs as a Windows scheduled task (`gpu-thermal-logger`: at logon and every 5 minutes, a start ignored while it runs; 60 s interval, the Prometheus default, costing about 0.1% of one core: standard: findings/monitoring-sample-interval, checked 2026-11-17), independent of any chat. The logger moves lines of earlier months to `thermal-YYYY-MM.jsonl` (`scripts/guard_logs.py`); `thermal.jsonl` is always the current month, and the reports read the archives too. It appends GPU temperature, power draw and NVIDIA's thermal-slowdown counters (and the hottest CPU core when Core Temp is running) to `~/.gpu-guard/thermal.jsonl`. Each round checks the newest sample there; if it is over 3 minutes old, the round restarts the task (`schtasks /run /tn gpu-thermal-logger`) and the morning summary names the gap. Never stop the task when the loop stops. The morning summary gives the night's peak GPU temperature, the minutes at or above the card's target temperature (87 °C on this laptop, read from `nvidia-smi -q`), the minutes at or above its slowdown temperature, and any thermal-slowdown time, from `gpu_run.py report --thermal --since <start time>` (standard: findings/laptop-thermal-tiers, checked 2026-11-14).

**Cooling check and health report** (user's decision, 2026-11-16: "automatic"). Right after checking the thermal logger and before any heavy job, run `python ~/claude-config/scripts/laptop_health.py due`. If it exits 1 (no cooling reference in 7 days), run `python ~/claude-config/scripts/gpu_run.py run --resource ram --wait -- python ~/claude-config/scripts/laptop_health.py reference --note "overnight start"  # estimate: 12m` and wait for it; it takes about 12 minutes, runs nothing on the GPU, and, once three runs exist, skips itself at no load when the room looks unlike the usual (AC on). A skipped night is retried the next night; say in the morning summary whether it ran, was skipped or aborted. It measures the laptop, so Kaggle-first (working rules) does not apply to it. At the end of the run, the morning summary also gives `python ~/claude-config/scripts/laptop_health.py report --days 1` output (heavy hours, heat-cool cycles, GB written, SSD and HDD health, battery, hardware errors); the logger takes the before and after snapshots itself (standard: findings/laptop-cooling-baseline, checked 2026-11-16).

**GPU clock cap** (user's decision, 2026-11-17, claude-config issue #22). Before the first heavy laptop job, run `schtasks /run /tn gpu-clock-cap-on` (an elevated task running `nvidia-smi -lgc 1000,1350`, registered once by `setup-machine.ps1` with one admin approval, none per night). At the end of the run, and before any job that times this laptop's speed, run `schtasks /run /tn gpu-clock-cap-off` (`nvidia-smi -rgc`), then cap again after it. The cap clears on reboot. The morning summary says whether the cap was on.

**Thermal watchdog** (user's decision, 2026-11-18). `gpu_run.py run` and `gpu_run.py hold` read the GPU temperature every 15 s while a GPU job runs or a held GPU service is up, against the card's own limits from `nvidia-smi` (defaults 80 and 92 °C when it reports none). It logs `thermal_warn` to `events.jsonl` and prints a line when the GPU has stayed at or above Target Temperature minus 7 °C for 5 minutes or the thermal-slowdown counter rises, and logs `thermal_stop`, ends the job (`run`) or `docker stop`s the held containers and logs `thermal_stopped` (`hold`), exit code 4, when it has stayed at or above Slowdown Temp minus 3 °C for 2 minutes. The `thermal_alert_check` hook tells each chat about a new event. After a stop, do not restart the job unchanged: check the cooling (`laptop_health.py report`), name the stop in the morning summary, and run the cap benchmark (it is then due). Ollama use outside the lock is not watched (it has no process to stop; the morning report and `gpu_run.py check` flag it; the checker's choice, 2026-11-18, issue #24). Safety limits from the card's own figures; the minutes are the checker's choice, to review after the first real alert.

**Cap benchmark** (user's decision, 2026-11-17, claude-config issue #23). After the cooling check, run `laptop_health.py due --kind cap-bench`. If it exits 1 (none yet, the GPU driver version changed, or the thermal watchdog fired since the last one; there is no calendar interval: user's decision, 2026-11-18, keep a sensible cap and re-measure on a signal), run `gpu_cap_bench.py` under the GPU lock at 1200, 1350, 1500 MHz and uncapped, in that order. For each setting, run Ollama generation back to back and stop as soon as the run is stable: the mean GPU temperature of the last 30 s is within 1 °C of the 30 s before (drift, not swing: the fan cycles the temperature by a few degrees; user's change from a 1 °C max-minus-min band, 2026-11-18, after two runs never reached it) and tokens/s vary by at most 2% (coefficient of variation) over the last 5 requests, after at least 60 s and at most 4 minutes (then record "not stable"). The stable window is the measurement. It appends tokens/s, mean temperature, mean power, tokens per joule, AC or battery state, room-proxy and driver version for each setting to `health.jsonl`. The morning summary shows the table and says whether 1350 is still the best setting (lowest temperature within 20% of uncapped speed). A run on battery power is refused. Basis: `findings/gpu-benchmark-warmup-duration`; the thresholds are the checker's choice from one run, so review them after the first benchmark.

**Heavy-task hold** (user's decision, 2026-11-18, claude-config issue #26, after one night's right pick produced nothing because its worker was killed twice under low memory and the loop was stopped for a peer's GPU test, and another night spent 90 minutes queued on the locks). An issue is *heavy* when it carries the `heavy` label: its finish needs a GPU job, a full test suite, a large model or dataset load, or a Compose stack. Triage sets the label (`TRIAGE.md`) and the loop sets it when it files an issue; a label, not the finish-line text, because `next_task.py` already reads labels and prose is not reliably machine-readable. Each round's `next_task.py` runs `gpu_run.py status` when a heavy issue is startable; if the GPU lock is held or free memory is under the 4 GB gate it prints `HEAVY HOLD: <reason>; skipped heavy #n; take #m`. Take #m (the next startable issue that is not heavy), list each skipped heavy issue with the reason in the morning summary, and look again at the start of the next round (the check repeats by itself, so nothing is stored). A worker killed for low memory is not retried at once: put `heavy` on its issue if missing, comment the kill, release the claim, and let the issue wait for the next clear check.
