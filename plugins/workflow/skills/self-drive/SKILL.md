# Self-driving chat

(User's decision, 2026-10-31: per chat, started by the user's prompt only; saved globally so any project can use it. Standard: Kanban pull system, where a worker takes the next ready item when it has capacity, with a WIP limit; checked 2026-10-31.)

A chat never starts this by itself. The user starts it in a chat by asking, and it lasts until that chat ends or the user says stop. It does not change any project limit: a project's `CLAUDE.md` hard limits, user-merge paths and queue limits all still apply.

## Start

Invoke the `loop` skill (Skill tool, skill `loop`) with no interval (the model paces itself) and this brief as its prompt. Running the brief once in the current turn is not a loop: the run then ends with that turn (user's decision, 2026-11-14, after an overnight run did exactly that and stopped after 2 minutes). If the project uses the `workflow:multi-chat` protocol, load that skill first and follow its claim rules.

> Each round:
> 1. Sync: run `python <this skill's folder>/next_task.py --status` in the repository (add `--handoff <path>` if the project has a handoff repo). It pulls the handoff repo if given and prints, in one output, open PRs, claimed issues, worktrees and the startable issues. Use that output for steps 2 and 3; do not repeat those checks with separate `gh` or `git` calls in the same round (user's decision, 2026-11-14: each loop-chat call re-reads its whole context, and status checks were most of its calls).
> 2. **Review first** (only in review mode `peer`; in other modes merge your own PRs as that mode says, see `workflow:pr-review`, "Review modes"). Take the oldest open PR with no review comment from a chat other than its author and review it as `workflow:pr-review` says. Never review your own PR.
> 3. **Then work.** Run `python <this skill's folder>/next_task.py` in the repository. It lists the startable issues bottleneck-first (multi-chat skill, "Bottlenecks first"); take the first one the rules below let you take (check `main` and the issue for existing work, such as a design brief, code or a ticked box, before routing; a task already done is closed out, by ticking the box and releasing the claim, not redone; user's decision, 2026-11-14, after three workers were routed to work that already existed), and make the `fix:` lines it prints (a missing dependency link or `priority:now` label) on the way. If it cannot reach GitHub, take `priority:now`, else the oldest unblocked `priority:next`, else the oldest unblocked `priority:later`. Claim it as the project says (label plus a comment listing the files) and verify the claim. Then route it, so the loop chat's context stays small (user's decision, 2026-11-14; standard: findings/long-agent-run-context and findings/agent-delegation-choice, checked 2026-11-14):
>    - (a) a short task with a checkable finish goes to one worker subagent (`workflow:subagents` applies; starting self-drive is the user's ask): `isolation: "worktree"`, Sonnet unless the issue's tag names Opus, a tight brief (issue number, files, the check to run, any GPU-lock command), a report of at most 10 lines (PR link, files changed, checks with results, open questions). The worker runs lint and tests, commits, pushes its branch and opens the PR with `Closes #n`. The loop chat does not read the diff or any log; it verifies from small sources: `gh pr checks`, `gh pr diff --stat` (the file list matches the brief and no user-merge path is touched unless intended) and the PR body's closing line. A finished Kaggle run goes to a worker with the run id; the loop chat never opens its log or output. On a user-merge path, or when the report and `--stat` disagree, the loop chat reads the diff itself (user's decision, 2026-11-14; standard: findings/agent-worker-scope-and-verification, checked 2026-11-14). A worker may take up to 3 small issues in a row when each is in the same repository, touches files no other claim holds, and has its own checkable finish; the loop claims each before dispatch, the worker opens one PR per issue, and its report lists each PR (at most 10 lines in all). (User's decision, 2026-11-14. Why: each worker pays about 45K tokens of startup context before any work; measured 2026-11-14.);
>    - (b) a long task (a measurement run, about an hour or more) goes to a background session: `claude --bg -n <issue>-<slug> "<brief>"` from the main checkout (on a machine without `claude` on PATH, the VS Code extension's bundled `claude.exe`). It works in its own worktree and opens its own PR; the loop chat reads only the PR and `claude agents --json` state. The brief says: create the worktree with `git worktree add ../<ID>-<slug>` (never `EnterWorktree` or `--worktree`), pass the PR body as `--body-file` (never `--body -`), and finish with `gh pr view <n> --json closingIssuesReferences`. When the worker is done, the loop chat checks that the PR body has `Closes #n` (fixing it if not), removes the session with `claude rm <id>`, and checks `git worktree list` for a stray worktree under `main/.claude/worktrees` (first real run, 2026-11-14, hit all three: a stray locked worktree, a PR body of just `-`, and a finished session left running);
>    - (c) a task done in a couple of tool calls stays in the loop chat.
>    One worker at a time. Then start the next round.
> 4. **Route or skip** an issue:
>    - needs an architecture or design choice: write a brief in the project's design folder, open it as a PR, move on;
>    - touches a path the project reserves for the user (the project's `CLAUDE.md` lists them; in solo-fast by default infra, deploy config, secrets, money, lockfiles by risk, and a `.claude/` change that loosens a guard, see `workflow:pr-review`): do the work and open the PR with `needs-you` and the user as reviewer, while that queue is under the project's limit (default 3); the gate is the merge, not the work;
>    - needs a measurement, GPU or free-quota cloud run (Kaggle): in overnight mode, run it (local GPU through `gpu_run.py run --wait` with an `# estimate:`; a cloud run with the project's own runner, waiting on it in the background, not polling); in daytime self-drive, skip it (user's decision, 2026-11-14; the free-cloud exception is in the working rules' Hard limits);
>    - skip (leave it, say nothing more) only when it: carries `needs-you`; needs a decision only the user can make; involves secrets; calls a paid API at scale; overlaps a file another chat has claimed; or needs a tool the machine lacks, or (in daytime) a large download, or in overnight mode a download that needs money or does not fit on disk;
>    - (overnight mode only) a free large download (model weights, a Docker image) is allowed once free disk space is checked (keep at least 20 GB free on the system drive); a free-tier deploy and creating a new repository are allowed under the working rules' overnight exceptions; skip only when the step needs money, a credential the agent may not read, or does not fit on disk (user's decision, 2026-11-14).
> 5. **Stop** the loop (do not schedule another round) when: no issue is left that steps 3 and 4 can take (daytime only; in overnight mode the loop files new issues instead, see "New issues" below); the project's limit on items waiting for the user is reached; three different tasks in a row each fail CI twice (a likely shared cause; say so); or you are unsure the task is yours. A task whose CI fails twice is parked, not retried: leave its PR as a draft, remove `needs-you`, record the failure and the untried fix in the summary, and take the next eligible task (user's decision, 2026-11-14; standard: findings/agent-loop-stop-on-repeated-failure, checked 2026-11-14). Before stopping, run `next_task.py --limit 100` and list every issue it prints with the step-4 bullet that rules it out; an issue that needs an architecture or design choice is not ruled out: write the brief and open it as a PR. "Lower priority", "did not read it" and "touches `.github/`" match no bullet, so take the issue (user's decision, 2026-11-14). Never ask the user what to do next; say why it stopped in one line (user's decision, 2026-10-31; standard: bounded autonomy, where an agent escalates only at the edge of its authority and halts on explicit stop conditions, and Kanban pull of the next ready item; checked 2026-10-31).
> 6. Between rounds say nothing unless something blocks the user. When the loop stops, give one line: what was done (PR links) and why it stopped.
> 7. **End every turn with `ScheduleWakeup`**: the last tool call of a round is `ScheduleWakeup` with this same prompt (a delay of 60 seconds or more), or `stop: true` when step 5 says to stop. Since Claude Code 2.1.319 a turn that ends with neither ends the loop at once, with no fallback wakeup, and nothing tells the user. This holds after a turn that waits on a background session or a GPU job too (user's decision, 2026-11-14; standard: findings/overnight-agent-runs, checked 2026-11-14) A `Stop` hook (`loop_guard.py`) backs this rule: when a turn ends with no wakeup pending and no background task running, it tells you to schedule or stop, once per turn (user's decision, 2026-11-14; standard: findings/agent-loop-control-enforcement, checked 2026-11-14).
> 7a. **Context reset (overnight mode only).** At the end of a round (PR opened, task parked, or a Kaggle wait started), run `python <this skill's folder>/context_size.py <session-id>` (the session id is the folder name in your scratchpad path). If it prints more than 200000, write the resume note (round number, open PRs, claimed issue, what the next round starts with) to the morning-summary file, start the successor with `claude --bg -n selfdrive-<n> '<this brief>; resume note: <path>'` from the main checkout, confirm it appears in `claude agents --json`, and only then end this chat with `ScheduleWakeup` `stop: true`. If the successor does not appear, keep going in this chat and say so in the summary. The successor's first round reads the note and the morning-summary file. Never run two loop sessions at once (user's decision, 2026-11-14; standard: findings/agent-session-handoff-reset, checked 2026-11-14; the 200K threshold is a local measurement, not a sourced figure: a call there costs about 12K weighted more than in a fresh 80K chat and a handover costs about 100K, so it repays in about 9 calls).

## Pacing

After opening a PR, start the next round at once in a new worktree; do not wait for its review or CI (user's decision, 2026-10-31; standard: Kanban pull with a WIP limit on review, about 1-2 items per reviewer, and background coding agents such as Copilot coding agent open a PR and move on; checked 2026-10-31). Wait only when:

- 2 of your own PRs are open with no review yet (review mode `peer` only): review others' PRs, or schedule the next round in 5 to 10 minutes;
- the next eligible task depends on an open PR's change.

When nothing is eligible, stop rather than poll (overnight mode files new issues instead, see "Overnight mode"). Never schedule waits shorter than 60 seconds.

## Stopping

The user stops it by telling the chat to stop. The chat then ends the loop and finishes or parks its current task (commit as `wip:` on its own branch if unfinished).

## Overnight mode (user's decision, 2026-11-13)

The user starts it by asking a chat to "self-drive overnight". It is the loop above with the extra rules below. The project's merge mode, user-merge paths and `needs-you` queue limit all still apply, so a solo-fast project merges after its usual check. There is no cap on PRs, rounds or hours: the loop ends when three different tasks in a row each fail CI twice, the project's `needs-you` queue limit is reached, or the user stops it (Esc while the chat waits; otherwise tell it to stop). (Departs from standard: findings/overnight-agent-runs recommends caps on iterations, spend and time; the user chose none, relying on the harness suspending a chat at its usage limit, 2026-11-13.)

**Before the first round**, check what you can and say in one line what the user must do: `gh auth status` shows the bot, the working tree is clean, the `keep-awake` status line shows a hold. Usage credits must be off (the user checks at claude.ai/settings/usage; you cannot see it), so a usage limit pauses the run instead of billing it. Never turn on usage or API credits. That one line names the keep-awake hold you saw, or says none is shown. Then record where `main` stands: run `git fetch`, then create the morning summary file at once with one line, `Start: <output of git rev-parse origin/main> (<repo>, <date and time>)`, so the starting commit survives a crash or a context reset (user's decision, 2026-11-14). Also tell the user to start Claude Code for an overnight run with `CLAUDE_CODE_LOOP_KEEPALIVE=1` set (read at startup; you cannot set it for a chat already open): it restores one fallback wakeup about 20 minutes after a turn that forgot step 7, a safety net and not a substitute (standard: findings/overnight-agent-runs, checked 2026-11-14).

**New issues** (user's decision, 2026-11-14; no cap). When no startable issue remains in overnight mode, the chat files new issues and then works them, so the run does not stop for lack of work: "no issue left" is not a stop reason in overnight mode, while the other step-5 stop reasons and the user's stop still apply. Each new issue must: trace to a finding in a merged PR or a measurement, or to a gap against the project's stated goals; be searched for duplicates first (`gh issue list --search` and the existing docs and ADRs); carry a `priority:` label with a one-line reason; have a checkable finish; and never be a decision for the user or need a user-merge path unless it fits within the `needs-you` queue limit. The claim rule applies as for any issue. **Goal gaps first** (user's decision, 2026-11-14). If the project's `CLAUDE.md` names a gap list (a file of skills or features the project should show, ranked), file new issues from its top uncovered items before any other new issue. An item is uncovered when no merged PR or open issue covers it; check that first. Take only items finishable in one night with the tools on the machine; a gap that needs money, a user decision or hardware the machine lacks is skipped and named in the morning summary. A fix or a measurement that does not serve a listed gap is filed only when nothing on the list is startable. This changes the order of new issues only; an existing open issue's `priority:` label is unchanged. The list holds no posting names, so a public repository may carry it. (Departs from standard: findings/overnight-agent-runs, which recommends caps; the user chose none.)

**Dependent work.** If the next task needs a PR that is waiting for the user, branch from that PR's branch and open the new PR against it (stacked). When the lower PR changes or merges, bring its changes into yours with `git merge`, never a rebase and never a force-push (the `push_guard` hook refuses every force). If the merge conflicts and you cannot settle it in the round, leave the PR for the user and say so in the summary. Skip the task if the lower PR is not yours. (standard: findings/agent-autonomy-tiers, checked 2026-11-13)

**Morning summary.** Write `overnight-<date>.md` in the project's handoff folder (none: put it in the final message): per PR the link, merged or waiting, key decisions, what was skipped and why, the stop reason, the time of the last round, the starting commit of `main` (from the file's first line), and the undo: for the whole night, `git revert <start>..origin/main` (a new commit; never reset `main` or force-push; a merge commit needs `-m 1`), or per PR what its own revert is. The last-round time shows whether the loop ended at a usage limit, which no source settles (the docs say nothing on whether a loop wakeup resumes after a limit resets). End with one line pointing to it. The summary is not optional: the final message names the file's path, and a stop message with no path means the run skipped this step (user's decision, 2026-11-14). (standard: findings/overnight-agent-runs, checked 2026-11-13)

**Cost log** (user's decision, 2026-11-14). At stop, run `python <this skill's folder>/selfdrive_cost.py --repo <owner/name> <session ids of this run and its successors> --label <repo>-<date> --log ~/.claude/selfdrive-runs.jsonl` and copy its `weighted_M`, `loop_M`, `workers_M`, `prs_merged` and `weighted_M_per_merged_pr` into the summary. A change meant to cut tokens counts as better only if weighted per merged PR falls over at least 3 runs against the runs before it, with the merged share and parked tasks no worse (baseline 2026-11-13/14: 0.46-0.62M per merged PR; one loop per repo, since the PR count takes every bot PR opened in the run's time window). (standard: findings/long-agent-run-context, checked 2026-11-14, which names tokens per merged PR from the transcripts as the way to check)
