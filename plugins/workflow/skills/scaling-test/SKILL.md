# Testing scaling problems on a small budget

User's decision, 2026-11-01, after a vector-store experiment in a RAG project could only compare two stores on 164 real chunks. Used with `workflow:experiment` (which decides what to compare and by when) and `workflow:adr` (numbers go in a measurement note, the ADR keeps one line).

## When to run it (user's decision, 2026-11-01; standard: standards/heavy-job-scheduling, checked 2026-11-01)

Size the job before starting it: expected duration, RAM and CPU. A local job that would run over about 15 minutes, or take most of the RAM or cores, does not start now. Ask the user for a window with `AskUserQuestion` (tonight at a given time, or "when you say you are leaving"; recommended first), and say what the slowdown would be. Never choose the window alone. For a chosen time, register it with `schedule-heavy.ps1` next to this file (`pwsh -NoProfile -File schedule-heavy.ps1 -Name <task> -At '<time>' -Run '<command>' -WorkDir <dir> -Log <file>`): it wakes the computer, starts only on AC power, stops after `-MaxHours`, runs through `keepawake.ps1` and deletes its own task. The wake-up needs "allow wake timers" in the power plan, which an agent does not change; ask the user to check it once. Put the log path and the expected finish in the issue the run belongs to. The next chat that opens with the issue reads the log's last line (`== finished ... exit=<code>`) and reports the result in its first message; there is no other reminder. A job too big for the machine is a cloud-spend question (below).

## Steps

1. **State the question and the knee you expect.** What size or rate do you expect to break first (memory, latency, recall, build time)? A test with no expected breaking point only confirms that small sizes work. (standard: standards/scaling-tests-on-a-budget, checked 2026-11-01)
2. **Do the memory and disk arithmetic first,** on paper, and compare it with what the machine can give the test (RAM, the container limit, free disk). Put the numbers in the test notes. If the target size does not fit, say so before starting; "does not fit on a small machine" is itself a result. Check the machine (`Get-CimInstance Win32_ComputerSystem`, free disk) instead of assuming.
3. **Ramp in steps,** for example 10x, 30x, 100x of today's size, and stop at the first step that fails or bends the curve. Never jump to the target size. Watch memory while it runs, set a hard memory limit on each container, and stop at a threshold you chose in advance. Start a long local job as a background tool command, so the `keep_awake` hook blocks idle sleep until it exits; a job started any other way (foreground, Task Scheduler, a separate terminal) runs inside the keep-awake wrapper next to this file (`pwsh -NoProfile -File keepawake.ps1 -Run '<command>'`, which blocks idle sleep only while the command runs). Either way: a laptop's idle-sleep timer counts a busy job with no keyboard input as idle, and Docker may not recover after a resume. Never change the user's power plan. After a run that failed with no error, check the sleep events (`Get-WinEvent -FilterHashtable @{LogName='System'; ProviderName='Microsoft-Windows-Power-Troubleshooter'}`) before blaming memory. (user's decision, 2026-11-01, after a sleep ended a scale-up run) A scaled-down environment does not scale linearly, so read the curve and do not extrapolate it far. Find the knee in the small environment and treat any projection beyond it as a risk signal, not a result. (standard: standards/scaling-tests-on-a-budget, checked 2026-11-01)
4. **Warm up, then measure the same way for both sides.** Run `ANALYZE` (or the equivalent) after a bulk load, let index builds finish, run a warm-up pass, and discard it. Same inputs, same rate, same machine state, one path at a time. A result that flips after a warm-up step was an artefact: record it as one and do not use it.
5. **Compare at matched quality.** For search and other approximate systems, sweep the quality knob (for example `ef_search`) and compare latency at the same recall, not one setting per side. Measure recall against an exact scan, and use your own filters and your own data shape. (standard: standards/scaling-tests-on-a-budget, vendor-adjacent sources, so check the method on your own data; checked 2026-11-01)
6. **Fake every paid or rate-limited dependency.** Run load tests against fakes or simulators (an LLM simulator, a mock email or payment API) so the test costs nothing and measures your own system. Give the fake realistic latency (for an LLM: time to first token and delay per token) and inject the errors the real service returns (429, 5xx, timeouts); a fake that answers instantly makes the results look better than production. Keep the load profile honest: do not cut think times or shorten sessions to fit the machine. A fake says nothing about the provider's latency, quality or cost; check those with a small run against the real service, which costs money and so is asked first. (standard: standards/scaling-tests-on-a-budget, checked 2026-11-01)
7. **Label what is synthetic,** in the table and the note: copied rows, random vectors and generated queries are not real data. Copies of the same vectors are easier than real data for an approximate index. Real queries and real distributions need real data.
8. **Report limits next to the numbers:** machine, sizes, run length, number of samples, what was not tested. Tail percentiles (p99) need enough samples to mean anything.
9. **Clean up.** Delete the containers, volumes and test data you created, and release any claimed resource (for example the Compose stack in a multi-chat project).

## Ask first

Anything that costs money (a cloud machine, a paid tier, a managed database) or runs longer than the working rules' threshold needs the user's yes first, with the sizes, the price limit and what the test will show. Make a cloud run short-lived: create the machines at the start, destroy them when the run ends (with a hard time limit as a backstop), and run the full ramp locally first so the cloud run checks only the largest step. Spot or preemptible machines cost less but can be interrupted; use them only for a run that can restart. (standard: standards/scaling-tests-on-a-budget, checked 2026-11-01) A local run that may exhaust the machine's memory needs the ramp and limits above, and a message to the user before the largest step.
