# Pull requests: open, review, merge

Moved out of the working rules (`~/claude-config/rules/working-rules.md`) on 2026-10-30 so it loads only when needed; the text is unchanged. The project's `CLAUDE.md` may make any of this stricter.

## Merging in a solo-fast project

A confirmed **solo-fast** tier (recorded at the top of the project's `CLAUDE.md`) is the user's standing exception to the Hard limits' "ask before merging a PR"; nothing else in the Hard limits is relaxed by any tier. In solo-fast, agents open PRs freely; any chat other than the author reviews and enables auto-merge; the user merges only PRs touching the paths the project's `CLAUDE.md` lists (default: infra and deploy config (files that build or run production or CI; local-only dev files, such as a compose file for the dev stack, are not deploy config), lockfiles by risk (the reviewer lists every changed package and may merge new packages and patch or minor bumps from the default registry with hashes kept; the user merges a major bump, a package the PR does not name, a new registry or git source, or removed hashes), secrets, money; user's decision, 2026-11-01). `CLAUDE.md` and `.github/` are ordinary files, checked by the reviewer, unless the change touches a user-merge item above such as deploy steps or secrets (user's decision, 2026-11-01: agents already ask the user through `AskUserQuestion` before any rule change, so the extra merge step added nothing; a project may list them again). Agent config (`.claude/` settings and hooks) is drawn by risk: the reviewer reads the diff with extra care and says in the PR comment what it checked, and the user merges it only when it adds a permission allow rule, removes or disables a hook, or makes a hook refuse less (user's decision, 2026-11-01, after 30 user merges showed no recorded review from the user; the risk the gate answers is an agent loosening its own guard; standard: findings/agent-config-protection, checked 2026-11-01). Public positioning is not on the solo-fast list: README and other docs are ordinary files, and the reviewer checks that a change describing what the project does matches the code before merging it (user's decision, 2026-11-01; stricter tiers keep public positioning as a user-merge item). Licensing, repository visibility and anything a project's `CLAUDE.md` lists stay the user's through the Hard limits and Decision rights. In the **standard** tier agents push branches and the user opens and merges PRs; in **strict**, the user also reviews every diff before merge.

solo-fast needs the permission rules `Bash(gh pr create:*)`, `Bash(gh pr comment:*)` and `Bash(gh pr merge:*)` in the project's `.claude/settings.local.json`; the user adds them. An allow rule matches only a command that starts with it, so run these commands plain (`gh pr create --repo … --body-file …`), never chained after `cd … &&` or with `$(…)`; a chained call falls to the auto-mode classifier and is denied.

## Review modes (user's decision, 2026-11-01)

One global setting, `~/claude-config/settings/review.json` (`mode`, `since`, `why`), says how a pull request is checked before an agent merges it, in every project and tier. The `review_mode` hook tells each chat the live value at start and again when it changes; a missing or unknown value counts as `peer`. The user changes it; a chat edits the file only when the user asks. A project's `CLAUDE.md` may pin a stricter mode for itself. In the standard and strict tiers the user already merges or reviews, so in practice the mode changes solo-fast.

| mode | before `gh pr merge <n> --auto --squash` | measured cost |
|---|---|---|
| `peer` | a named peer chat reviews as "Review and merge" below (`/code-review medium`, deeper on risky paths) and posts the comment | about 1.3M input tokens and 7 calls per review, plus a chat to hold it |
| `self-review` | the author runs `/code-review low` on its own PR and fixes or tracks each finding | up to about a peer review, scaled by the author's context |
| `self-diff` | the author re-reads its own diff once against the blocking-issue list below | about one call |
| `ci-only` | the author enables auto-merge; required checks are the only gate | none |

Cost is a median of 14 reviews in one project's transcripts (standard: findings/agent-review-cost, checked 2026-11-01). In every mode: Hard limits, required checks, the user-merge paths and the `merge_gate` hook (workflow plugin: refuses a merge outside solo-fast, on a user-merge path, with a check that has not passed, or `--auto` with no required check; the user-merge paths it reads are the ones the repository's CODEOWNERS on the base branch gives an owner, or a default list when there is no CODEOWNERS, plus secret files always; user's decision, 2026-11-11, so a project's path list has one copy) are unchanged; a user-merge item still goes `needs-you` to the user, and a blocking issue still stops the merge. Outside `peer`, the author may enable auto-merge on its own PR (author ≠ approver applies to agent review only in `peer`), there is no named reviewer or review comment, and the PR body says `Review mode: <mode>`. A project rule that asks the reviewer to do something at merge (a DONE.md line, say) falls to the author.

**No required checks** (user's decision, 2026-11-05): on a repository with no required checks (GitHub Free, private), `--auto` is not a gate. Run `gh pr checks <n> --watch` as one command and, only if every check passes, `gh pr merge <n> --squash --delete-branch` as a second, separate command. Never chain them (`watch | tail; merge`, `watch && merge`): the `merge_gate` hook reads the checks before the command starts, sees them pending and refuses the merge (6 of 7 merge refusals in one project's transcripts, 2026-11-05 to 2026-11-12) (standard: findings/auto-merge-without-protection, checked 2026-11-05).

## Review and merge (standard: see Sources below, checked 2026-10-29)

In `peer` mode this section applies as written; in the other modes, only the blocking-issue list, the user-merge rules, "After a merge" and "Post the review" (for `self-review` findings) apply.

Sources: GitHub's rules for required approvals and for Copilot-agent PRs, GitHub team review auto-assignment, Google/Chromium OWNERS review, and published guidance on agent approval authority.

- **Author ≠ approver.** This is the one fixed rule everywhere: GitHub does not count an author's own approval, and whoever assigned a Copilot agent cannot approve its PR. A chat never reviews or merges its own PR, and an agent-authored PR that an agent approved counts as unreviewed by anyone independent.
- **General review comes from a pool, not a dedicated reviewer.** This matches GitHub's team auto-assignment (round robin or load balance) and Google's LGTM, which any engineer can give. Chats of the same model with the same `/code-review` recipe gain nothing from a "reviewer" role. What gives a review its value is independence (a fresh context without the author's assumptions), and a dedicated reviewer chat becomes a bottleneck that idles until prompted. Chats serve the pool by named assignment: the author picks one reviewer, idle first (see the `workflow:multi-chat` skill).
- **Specialize by risk, not by agent.** Industry practice puts named owners on risky paths (CODEOWNERS, Google OWNERS and readability). Here the user is that owner: risky paths (`.github/` risk items, `infra/`, auth, secrets, lockfiles outside the by-risk rule, money, and in stricter tiers public content) get a deeper review (`/security-review` or `/code-review high`), and the user merges them. Everything else gets `/code-review medium`.
- **Merge authority follows the gate, not the person.** On GitHub anyone with write access may merge once the ruleset is satisfied. So the reviewer does not merge by hand: when the review finds no blocking issue and the PR is not a user-merge item, it runs `gh pr merge <n> --auto --squash`, and GitHub merges when the required checks pass. Restricting merges to the lead adds no safety when every chat is the same model under the same account; it only adds a queue.
- **A blocking issue** is any of: a correctness or security finding the reviewer confirmed, a failing or pending required check, a secret, private identifier or local path in the diff, a touched user-merge path, or an earlier finding not addressed.
- **All chats act as one GitHub account** (the bot, `phuchai-bot`), so GitHub cannot tell author from reviewer, and a required-approvals count cannot enforce author ≠ approver. The inbox rule enforces it. The hard gates are required CI checks and the user-merge list.
- **For anything the user must merge**, request their review (`gh pr edit <n> --add-reviewer phuchaitt3`) and add the `needs-you` label with a comment saying in plain words what it changes, that checks and review are done, and which button to press. The bot cannot approve its own PRs, so agent reviews are comments.
- **Fallback** (no lead, user's decision, 2026-10-31): a PR with no peer to review it waits for the next chat that starts, which takes it as the oldest unreviewed PR. If it is still unreviewed after one business day, the first chat that sees it adds `needs-you` with the user as reviewer. It never goes to its author.
- **After a merge, refresh open pull requests:** the chat that merges, or that first sees a merge, runs `gh pr list --state open --json number,mergeable` and merges the default branch into each of its own pull requests that now conflicts (no rebase, no force-push), in the same session. A conflict in another chat's pull request goes to that chat through the inbox. A pull request waiting on review fixes is its author's first task, so it does not sit open for days (user's decision, 2026-10-30; standard: trunk-based development, short-lived branches).
- **Invest in checks over review.** Studies find agent-only review catches less than human review, and review attention fades with habit. Tests, typing, evaluation jobs and merge queues do not fade, so each one added is worth more than another review pass.
- **GitHub comments are for the record a human reads** (user's decision, 2026-10-30): review verdicts and needs-you notes. A message for another chat goes through SendMessage or the inbox, never a GitHub comment, because GitHub emails the owner and agents do not read notifications.
- **Post the review** as a PR comment (`gh pr comment <n> --body-file …`) stating the verdict, what was checked, findings dropped after checking, and for a `.github/` change, that no user-merge item is touched. If the comment is denied, save the text in the handoff folder, link it in the Review queue row, and continue.

## Deferred work

Before a PR merges, every deferred item (its "Not done" list, and each review finding not fixed in the PR) is an open GitHub issue, or a checklist line in one, and the PR or review comment links it; no bare TODO in code without an issue number (user's decision, 2026-10-30; practice: deferred work gets a tracking issue, review findings are fixed or tracked, checked 2026-10-30). In a public repository an issue never holds private content: that stays in a local ticket and the issue says only "private item; ask in chat".

Workflow work is never low priority (user's decision, 2026-10-31): a change to how agents work (rules, skills, `CLAUDE.md`, process docs, issue and PR templates, hooks) affects every chat from then on. A PR that changes a process updates every file that describes it in the same PR; if one is a user-merge path, the author opens a companion PR for it in the same turn, labelled `needs-you` with the user as reviewer, and links the two. Workflow drift found at any other time is fixed in the turn it is found, or opened at once as a `needs-you` PR if only the user can merge it; never queued as `priority:later` (standard: Google docguide "Update docs with code", checked 2026-10-31).

## Before pushing to an existing branch

Check its PR is still open (`gh pr view <n> --json state`). A merge takes only what was on the branch at that moment, so a later push is lost; after a merge, a follow-up goes on a new branch off the default branch. The `push_guard` hook enforces this.
